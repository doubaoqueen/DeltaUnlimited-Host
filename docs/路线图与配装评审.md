## 第一部分：配装设计评审（制式套装方案 v1）

### 总评

**方案合理，选型聪明，可以放心进真机实测。**

核心判断：用"游戏内置预设系统"替代全槽位标注，与 MAA 借游戏内置基建排班是同一思路——1 张模板（standard_set_card.png）+ 1 个坐标（416,933）就换来整套合法配装，成本比标注 8 个装备槽位低一个数量级。全槽位方案需要：槽位类型识别 + 物品名 OCR（美术字，已实测读不出）+ 物品图标模板库（几十张）+ 仓库导航，投入产出完全不成比例。

### 设计亮点（保持，不要动）

| # | 亮点 | 为什么对 |
|---|------|---------|
| 1 | 制式套装杠杆 | 借游戏既有系统，1 模板 + 1 坐标 = 整套装 |
| 2 | 扣券时机安全 | 确认配装才扣券，之前可 X 退出，天然支持迭代测试不烧券 |
| 3 | 状态迁移判断成败 | 不追 1.5s 瞬态 toast，"2.5s 内回配装界面=成功"，健壮 |
| 4 | preset_apply 不重试防双击 | 消耗按钮双击风险被显式规避 |
| 5 | 失败分支慢过渡兜底 | preset_apply_fail → detect → loadout?→confirm，慢过渡不误报 |
| 6 | 真机标定先行 | 截图验证、按钮区域标定，全部有 capture_20260922_184254.png 证据 |

### 优化点（按优先级，实测前建议至少完成 1、3）

#### 优化 1：均衡卡纯坐标缺闭环校验（中风险）

**问题**：`preset_balanced_button` 是裸坐标 (416,933)。若三张卡排列顺序变化或布局漂移，坐标会点错卡——点错不是失败，而是**换成生存/火力的券（更贵）**。状态迁移判断发现不了：它只看"回没回配装界面"，不看"扣的是哪张券"。

**方案**：用设计文档已验证的"额度计数可读"（右上"拥有：9/10 3/5 1/5"）做闭环：
- **最低成本版**：点消耗按钮前 OCR 计数区一次，成功日志带上读数，供事后审计；
- **进阶版**：确认配装前后各读一次，校验扣的是新兵券（10/10 那张）。

**附加价值**：这个读数就是将来 `budget_cap`（loadout_preset.json 已预留字段）的地基，一次标定两用。

**次级校验（可选）**：设计文档实测均衡卡按钮区域"仅读到券数 1"——若该数字稳定可读，可在点击前用它做存在性校验，防界面未加载完就点空。

#### 优化 2：if_screen 分发表复制了两遍（可维护性）

**问题**：enter_match.json v6 的 13 条 if_screen 在 Tab 前后一字不差出现两遍。加 preset_select、settlement 时都被迫改两处——结构已到临界点，下一个界面进来还会翻倍出错概率。

**方案**：引擎加 `dispatch` op，routes 表一份：

```json
"routes": {
  "plaza_first": "prep",
  "plaza_ready": "do_loadout",
  "space_continue": "skip_overlay",
  "mode_select": "pick_mode",
  "map_select": "start_action",
  "map_pool": "pick_zerodam",
  "loadout": "apply_standard_set",
  "deploy_reminder": "reminder_check",
  "matching": "wait_match",
  "char_select": "done",
  "settlement": "settlement_wait",
  "preset_select": "preset_apply"
},
"steps": [
  { "id": "detect_start", "op": "dispatch" },
  { "op": "key", "key": "tab", "wait_ms": 1500 },
  { "op": "dispatch" },
  { "op": "mark_unknown", "message": "..." }
]
```

routes 数组序即优先级（与现 if_screen 链顺序一致）。105 行 JSON 可缩到 ~70 行，加界面只改一处。纯引擎改动，不动识别逻辑。

#### 优化 3：失败原因被 1.5s toast 带走（体验）

**问题**：`preset_apply_fail` 进人工确认时提示早消失，mark_unknown 只能写"可能券不足或不符合规则"。且 `capture: after_preset_apply` 在 wait 1500ms 之后截图，toast 恰好 ~1.5s，证据基本错过。

**方案**：
1. 失败分支第一步**立刻补一帧证据**（fail 分支入口 capture）；
2. 补帧后加一次 `if_ocr`（keywords ["无法进入"]，顶部区域）尽力抓提示词写进证据——抓不到不损失，状态迁移兜底还在。

#### 优化 4：每局自动套预设 = 每局 5 万哈夫币（产品决策）

**问题**：v6 plaza_ready 分支无条件走配装。跑刀攒钱期可能想跳过配装直接出发（v3 行为）。

**方案**（二选一）：
- 简单版：保持两套 workflow（带配装 / 不带配装），按需选用；
- 更优版：引擎加 `if_flag` op 读 runtime.json（如 `auto_loadout: true/false`），一套链路两种行为。

不急，但别等 GUI 才做。

## 第二部分：项目路线图（单人节奏）

### 现状盘点

- **进场链路 90%**：lobby→Tab→plaza→地图池→部署面板→配装→制式套装→确认→入局提醒→匹配→干员选择（终点，人工）。缺：干员选择自动化；配装链路待真机实测。
- **工程底座全部成型**：WGC 截图、Windows OCR（含预处理+两级匹配）、模板匹配、具名区 zones、拟人输入（贝塞尔轨迹+铁律）、链路引擎（if_screen/if_ocr/wait_screen/mark_unknown/jump/detect）、加载期校验、xUnit 测试。
- **方法论已跑通**：真机标定清单 → 数据入库 → 链路接通 → 实测 → 回归固化。

### 阶段 A：进场收尾（当前，1-2 周量级）

- [ ] **A1. v6 真机实测**——设计定稿≠验证。重点观察：均衡卡坐标命中、2.5s 超时是否容得住慢过渡、计数回读（优化 1）。
- [ ] **A2. 干员选择自动化**——进场 100% 的最后一块：
  1. `ocr probe` 实测干员名（蜂医/红狼/威龙/深蓝等）可读性；
  2. 读得出 → ocr 策略点击；读不出 → 模板裁卡片 + 坐标兜底（同 zerodam_card 套路）；
  3. 标定确认进场按钮；
  4. 链路：`wait_screen char_select → click_element operator_xxx → click_element deploy_confirm`。
  5. 数据槽：elements.json 加干员元素即可，将来多干员选择再扩 operator.json。
- [ ] **A3. dispatch op 重构**（优化 2）。
- [ ] **A4. auto_loadout 开关**（优化 4）。

### 阶段 B：局内闭环（项目核心价值）

- [ ] **B1. patrol 接入 chain**——巡逻 v2 双守卫已是独立命令，包成 chain op。
- [ ] **B2. 拾取闭环**——`loot_prompt`（按F拾取）元素已定义：wait_ocr 出现"拾取"→ 拟人按 F。低频触发，符合安全红线。
- [ ] **B3. 撤离闭环**——`extract_marker` 模板定位 → 导航至撤离点 → 撤离 → settlement。v6 已会处理 settlement（按空格→重判→detect_start），撤离后**自动再进场**近乎免费。

**B3 完成 = 单局全自动闭环**：进场→配装→匹配→选干员→跑刀→撤离→结算→再进场。这是项目从"脚本集合"变成"完整自动化工具"的里程碑，建议在此点发第一个 release。

### 阶段 C：稳定性与可观测（与 B 并行）

- [ ] **C1. diagnose 命令**——ADR 已定：语言包可用性、模板有效性、区域回填体检，一条命令体检全套标记。
- [ ] **C2. 每局 summary**——各步骤耗时、OCR 命中率落日志。进场提速先测量再优化，不猜。
- [ ] **C3. OCR 标记回归测试**——fixture 截图断言全部界面标记命中。赛季更新后跑一遍测试即知哪些标记死亡，而不是链路跑到一半莫名超时。

### 阶段 D：扩展（闭环稳定后）

- [ ] **D1. 最小 GUI**——托盘面板：选链路、开始/急停、状态显示。
- [ ] **D2. Paddle 备用引擎**——按 ADR #10 门控，Windows OCR 当前实测够用（标签/按钮可读；卡名读不出已绕开），不急。
- [ ] **D3. 安全箱自动转移**——撤离后仓库格子点击（配装设计.md 已预留标注项）。
- [ ] **D4. 定制配装**——loadout_preset.json presets 填充 + budget_cap + 生存/火力卡按钮标定（GUI 选项入口）。

### 单人工程纪律（已在做对的，保持）

1. **真机标定清单 → 数据入库 → 链路接通 → 实测 → 回归固化**——配装这轮是范本。
2. **文档与代码同提交**——配装设计.md + 问题清单 + 订正模式很好，文档就是第二开发者。
3. **铁律入库**——拟人化参数保持随机范围，禁止固定值。
4. **测试保持绿**——数据/策略变更后同步修测试（depart_button coord→ocr 教训）。
5. **小步提交**——现有 commit 粒度和信息质量很高，继续。
