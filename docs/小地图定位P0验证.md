# 小地图定位 P0 验证报告（2026-10-21）

> 目的：验证"用局内小地图 ↔ 官方大地图做实时定位"的可行性（用户 2026-10-21 新导航方案的前置闸门）。
> 结论：**可行（用户肉眼确认 3/3 样本命中）**；精度与尺度稳定性待第二批验证。

## 1. 素材与工具

| 素材 | 来源 |
|---|---|
| 官方零号大坝底图（4096×3072） | `df.qq.com` 地图工具瓦片 `img/map_db/4_{x}_{y}.jpg` 拼接（188/192 瓦片，缺失 4 块在边界外），存 `screenshots/mapoverview/zero_dam_tiles_z4.png` |
| 官方标记坐标（1423 条物资点） | 同站 `js/lib/map_article.js` 的 `mapArticle2/3/4`（世界坐标 x/y+icon+大区域+条件），解析结果 `ai-training/runs/site_markers_all.json` |
| 世界坐标↔地图像素换算 | `js/lib/main.js` 的 `getMapPos`/`getSourceMapPos`（bj=128，xB2=81086.304688/128，yB2=80988.5/128，CRS.Simple 缩放 2^z） |
| 局内帧 | `ai-training/datasets/record/full/` 两局共 704 帧（1920×1080） |

**坐标换算（已验证：1422/1423 标记落图内）**：
```
lng = 128 - (centerX - worldX) / xB2      # centerX=358155.6875, xB2=633.486755
lat = -128 - (centerY + worldY) / yB2     # centerY=750191.75,  yB2=632.722656
px  = lng * 2^z                            # z=4 时 16px/单位
py  = -lat * 2^z
```

## 2. 方法

1. 小地图 = 左上角**圆形**面板（用户口述四点定圆：圆心 ≈(165,185)，半径 ≈120-129px，帧坐标）；
2. 圆形掩膜 NCC（归一化互相关，FFT 加速 + 积分图局部方差 + 低方差区域屏蔽），避免 HUD 边角干扰；
3. 多尺度搜索（模板缩放到 150-440px 的地图区域）；选**最高分**尺度（不按票数——小尺度在纯色区扎堆会导致误选）；
4. 位置→官方标记翻译：用最近标记的大区域名做语义核对。

## 4. 已知问题（第二批要解决）

1. **尺度不稳定**：同一局相邻帧命中的"最佳尺度"在 150/210/380 间跳动。可能是小地图缩放随场景变化，也可能是低分误选——需要"尺度先验 + 跨帧平滑"约束；
2. **精度未知**：目前只能说"落在正确区域"，没有量化误差（缺真值）。**真值来源**：游戏内大地图截图上玩家标记的位置（用户读数），或连续轨迹与移动速度的物理一致性检验；
3. **速度**：现在纯 Python + FFT，单帧多尺度约数秒——离线可用，实时（8Hz）需要 C# + 更快的实现（降分辨率/限制搜索窗口/尺度先验）。

## 7. 轨迹过滤与误定位根因（2026-10-21 下午）

### 7.1 误定位根因：UI 面板遮挡小地图

对 00:28:20-00:30:30 逐帧定位后发现 00:30:28 出现 **2 秒瞬移 1394px（≈265 m/s）**。查该帧 OCR：屏幕上是"**破坏物资室铁门 / 行动地点：水泥厂 / 报酬 30000 / 进行行动**"——**行动接取站面板**。结论：**交互 UI 面板会污染小地图区域，此时 NCC 仍给 0.6+ 分但位置全错**。

### 7.2 第二个坑：错误首锚

首帧定位（00:28:21，0.520 分）被直接采信为锚点，但随后 25 帧的候选全部远离它（被判"超速"）——说明**首锚本身是错的**，单帧低分不能当锚点。

### 7.3 解法：`LocalizerTrack`（`Vision/Localization/LocalizerTrack.cs`）

| 规则 | 说明 |
|---|---|
| 首锚需双帧确认 | 首帧候选挂起，第二帧候选与之一致（≤120px）才锁定 |
| 速度门 | 只接受相对上次确认位置速度 ≤30px/s 的候选（长空档按 30s 封顶，防放大瞬移） |
| 重锚定 | 连续 3 帧被拒但候选彼此一致（≤100px）→ 判定锚点漂了，重新锚定并报告 |

CLI：`dotnet run -- localizetrack "2026-10-12 00:28:20" "2026-10-12 00:30:30"` → CSV（接受/沿用/原因）+ 跳变统计。

**效果（同一时间段 67 帧）**：修复前 40 接受 / 27 沿用（错误首锚导致连续误拒）；修复后 **60 接受 / 4 沿用**（4 帧全部是真实误定位：1 帧无结果 + 3 帧 UI 遮挡/瞬移）。轨迹速度：**median 4.0 m/s、p90 7.2、max 11.9**（冲刺量级，合理）。

### 7.5 第三个坑：Tab 背包界面没有小地图（HUD 状态门，2026-10-21）

用户复核第 8 组（m2d，00:34:31）时指出："完全错误，左边甚至不是小地图，我估计是我打开的背包键时的界面"——**确认该帧是 Tab 背包全屏，左上角不是小地图**。这类帧定位器会把背包 UI 纹理当小地图匹配，得到"高分错误位置"（m2d: 0.648@180，位置全错）。

**修复两层**：

1. **screens.json 关键词修正**（`match_backpack`）：原 `require_all ["剩余离","本局收获","胸挂"]` 复测失败——"剩余离"常被 OCR 读成 刺余/离阎 等变体，严格匹配不稳。改为 **`["本局收获","胸挂","背包"]`**（三词实测均严格命中；结算界面无"胸挂/背包"，不串台）。
2. **`Vision/Localization/HudStateGate.cs`**：定位前先用 `ScreenDetector.Detect(frame, screens, group:"match")` 识别界面；命中 `match_backpack / match_map / match_settlement_*` 等全屏 UI 则判定"无小地图"、跳过定位（识别不到界面时 fail-open，交给轨迹过滤兜底）。`localize` / `localizetrack` 均已接入；`LocalizerTests.Fixture_BackpackFrame_IsGatedByHudStateGate` 用真机背包帧钉住。

**实测验证**：m2d 背包帧 → "⚠ 该帧为对局内 UI 界面（match_backpack），没有小地图，跳过定位" ✅；m2b 正常 HUD 帧 → 正常定位 ✅（212 测试全绿）。
