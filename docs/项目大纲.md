# DeltaUnlimited 项目大纲

> 版本：v0.3（大纲阶段，未实现）
> 定位：三角洲行动 · 烽火地带模式的"跑刀"自动化辅助 —— 低成本进场、拾取普通材料、撤离，积少成多缓解哈弗币压力。
> 红线：**不包含任何战斗/击杀辅助**，只做拾取与撤离流程自动化。

---

## 1. 愿景与边界

**要做的：**

- ComfyUI 式"积木工作流"：把游戏自动化需求拆成节点，一层层堆叠成流程
- 主 Agent（LLM）分析任务、分发工作给副 Agent（视觉/键鼠/调度/状态/导航/收益/安全）
- 副 Agent 调用节点引擎快速执行（截图 → 识别 → 决策 → 操作）
- 视觉路线：模板匹配 + OCR 双通道跑通，后期再微调 YOLO（`training/` 文件夹预留）
- BetterGI 式控制面板：任务开关一键启停、状态与日志展示（当前阶段核心入口）

**不做的（明确红线）：**

- ❌ 击杀/瞄准/自动战斗等任何对抗性作弊
- ❌ 修改游戏内存、注入、封包等非法手段（本架构只用屏幕截图 + 键鼠模拟，是"看得见的自动化"）

> ⚠️ 合规提示：任何游戏自动化都有违反用户协议、封号的风险。本架构仅用于个人学习与合规场景；设计上会加入拟人化与安全守卫，但无法保证不被风控识别，请自行评估风险。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────┐
│   GUI 控制面板（BetterGI 式任务开关）← 当前阶段主入口        │
└──────────────────────────┬───────────────────────────────┘
                           │ 开关 → 启停 workflow
┌──────────────────────────▼───────────────────────────────┐
│                   主 Agent（LLM 编排，暂为空壳）            │
│     接收目标 → 拆解任务 → 分发/监督 → 汇总结果 → 迭代        │
└──────────┬─────────────────┬─────────────────┬───────────┘
           │                 │                 │
   ┌───────▼─────┐   ┌───────▼─────┐   ┌───────▼─────┐
   │ 副Agent 视觉  │   │副Agent 调度  │   │副Agent 键鼠  │ ...共 7 个
   │ VisionAgent │   │ Scheduler   │   │ InputAgent  │
   └───────┬─────┘   └───────┬─────┘   └───────┬─────┘
           │                 │                 │
┌──────────▼─────────────────▼─────────────────▼──────────┐
│                 积木节点引擎（节点图执行器）                 │
│                                                          │
│  L3 任务节点     L2 逻辑节点      L1 感知节点     L0 基础节点│
│  (跑刀流程)     (状态机/分支)    (识别/定位)    (截图/键鼠)  │
└──────────────────────────────────────────────────────────┘
```

**当前路线（重要）**：主 Agent / LLM 暂为空壳预留（`agents/llm/` 留空实现，不接任何模型）。当前阶段由 **GUI 控制面板（BetterGI 式任务开关）** 直接驱动节点图 —— 点开关 = 启停一个 workflow。LLM 规划能力等雏形跑通后再决定。

**核心思想**：需求在最顶层（主 Agent），能力在最底层（节点），中间靠"副 Agent + 节点图"衔接。节点图是**数据**（JSON/YAML），可以组合、复用、版本管理 —— 这就是"积木"。

## 3. 积木节点系统（ComfyUI 式）

### 3.1 分层设计（一层层堆叠）

| 层 | 名称 | 作用 | 节点示例 |
|---|---|---|---|
| L4 | 编排层 | Agent 调度，把需求变成节点图 | 主 Agent、副 Agent 调用器 |
| L3 | 任务层 | 复合业务流程（大积木） | 跑刀全流程、拾取循环、撤离流程 |
| L2 | 逻辑层 | 判断与状态流转 | 状态机节点、IfNode、背包容量判断、收益评估、安全判定 |
| L1 | 感知层 | 把屏幕变成结构化数据 | 模板匹配、颜色识别、OCR（RapidOCR）、后期 YOLO 检测 |
| L0 | 基础层 | 直接操作系统 | 截图、鼠标移动/点击、按键、等待、日志 |

> 对应关系：ComfyUI 里 `CheckpointLoader → KSampler → VAEDecode`，这里就是 `Screenshot → DetectTarget → IfNode → MoveTo → ExtractAction`。

### 3.2 节点定义（接口统一，实现可替换）

```python
# nodes/core/base.py（概念示意，非最终实现）
class Node:
    name: str
    inputs: dict[str, InputSlot]
    outputs: dict[str, OutputSlot]

    def run(self, ctx: GraphContext) -> None:
        """从 ctx 读输入，写输出。子类实现。"""
```

**关键原则**：上层只依赖节点接口，不依赖实现。比如 L1 的 `DetectTarget` 节点，阶段一用"模板匹配 + OCR"实现，阶段二换成 YOLO 实现，**上层流程完全不用改**。

### 3.3 节点图（流程定义）示例

```jsonc
// workflows/knife_run.json（示意）
{
  "name": "跑刀主流程",
  "nodes": {
    "n1": { "type": "Screenshot",      "params": { "region": "screen" } },
    "n2": { "type": "DetectTarget",    "params": { "template": "assets/templates/loot_box.png" } },
    "n3": { "type": "IfNode",          "params": { "condition": "found" } },
    "n4": { "type": "MoveTo",          "params": { "x": "$n2.x", "y": "$n2.y" } },
    "n5": { "type": "InteractKey",     "params": { "key": "f" } },
    "n6": { "type": "LogAndWait",      "params": { "seconds": 0.5 } }
  },
  "edges": [
    { "from": "n1.out.screen", "to": "n2.in.screen" },
    { "from": "n2.out.found",  "to": "n3.in.condition" },
    { "from": "n3.out.true",   "to": "n4.in" },
    { "from": "n4.out.done",   "to": "n5.in" },
    { "from": "n5.out.done",   "to": "n6.in" }
  ]
}
```

### 3.4 节点引擎设计

- **注册表**：按类型名注册节点类（`Screenshot`、`IfNode`…），图里用字符串引用
- **执行器**：按拓扑序执行，共享 `GraphContext`（中间数据、变量、引用 `$n2.x` 取上游输出）
- **控制流**：IfNode / LoopNode / StateMachineNode 作为一等节点，图才能表达分支和循环
- **生命周期**：支持暂停、恢复、超时、**紧急停止**（安全守卫触发）
- **可观测**：每步执行写入日志和截图（`logs/`、`screenshots/`），方便事后复盘

## 4. Agent 编排层

### 4.1 主 Agent（LLM 规划）—— 暂为空壳

输入：用户目标（如"去零号大坝捡 5 个零件就撤"）
输出：任务计划 → 转换为节点图或副 Agent 任务队列
循环：执行 → 观察结果 → 判断进度 → 调整计划（有限轮次，防止失控）

> 当前阶段不实现，接口与目录先预留。

### 4.2 LLM 适配层（可切换）—— 暂留空实现

```python
# agents/llm/provider.py（示意，暂不接真实模型）
class LLMProvider(ABC):
    def chat(self, messages: list) -> str: ...

class DeepSeekProvider(LLMProvider): ...   # API 在线（待定）
class OllamaProvider(LLMProvider): ...     # 本地离线（待定）
# 配置里切换：{"llm": {"provider": "deepseek" | "ollama", ...}}
```

好处：以后想换模型/换服务商，只加一个 Provider 实现。**现在只建接口，不接任何模型。**

### 4.3 副 Agent 一览

| 副 Agent | 职责 | 主要输入 | 输出 | 依赖节点层 |
|---|---|---|---|---|
| **VisionAgent** 视觉 | 截图、目标定位、状态观察（模板+OCR 融合） | 截图请求 | 结构化观察 JSON | L1 |
| **InputAgent** 键鼠 | 移动、点击、按键（含拟人化） | 动作指令 | 执行结果 | L0 |
| **TaskSchedulerAgent** 调度 | 任务队列、推进、超时/重试 | 任务队列 | 任务状态 | 引擎控制 |
| **StateAgent** 状态机 | 游戏阶段、背包、位置状态维护 | 观察结果 | 状态更新 | L2 |
| **NavAgent** 导航 | 零号大坝点位、寻路移动、撤离点 | 目标点位 | 移动指令 | L1+L0 |
| **EconomyAgent** 收益决策 | 物品价值表、背包容量、何时撤离 | 背包状态 | 决策动作 | L2 |
| **SafetyAgent** 安全守卫 | 紧急停止、拟人化参数、合规校验 | 全局事件 | 停止/调整指令 | 全局 |

> 你问的"还有什么应该补充"：除了视觉、键鼠、调度，建议重点加 **StateAgent（状态）**、**NavAgent（导航）**、**EconomyAgent（收益）**、**SafetyAgent（安全）** 四个 —— 没有状态机流程会乱，没有收益决策不知道该捡什么、该不该撤，没有安全守卫出问题没法兜底。

### 4.4 主从协作时序（示意，LLM 接入后）

```
用户目标 ──▶ 主Agent(LLM) ──▶ 拆解任务清单
              │
              ├─▶ TaskScheduler: 排队执行任务
              │        │
              │        ├─▶ VisionAgent: "截图，找撤离点标记" → {found:true, x,y}
              │        ├─▶ NavAgent: "移动到 (x,y)" → 移动指令
              │        ├─▶ InputAgent: 执行移动/点击
              │        └─▶ StateAgent: 更新状态 {stage: extracting}
              │
              └─▶ 汇总结果 ──▶ 判断完成/继续/求助人工
```

### 4.5 GUI 控制面板（BetterGI 式，当前阶段核心入口）

交互参考 [BetterGI](https://github.com/babalae/better-genshin-impact)：一个主窗口，每个功能一个开关，点击即启停。

| 面板区域 | 功能 |
|---|---|
| 任务开关列表 | 每个开关绑定一个 workflow（节点图）：跑刀全流程 / 仅搜刮 / 仅撤离等 |
| 运行状态区 | 当前状态机阶段、最近一次识别结果、耗时 |
| 控制按钮 | 全局开始 / 暂停 / 紧急停止（含热键） |
| 日志区 | 实时日志（复用 core.logger） |
| 截图预览 | 最近一帧截图 + 识别框标注（调试利器） |

**实现原则（针对低配玩家电脑）**：

- 框架选 **PySide6**：高性能、生态成熟、好维护、资料多（对新手友好）
- **UI 层做薄**：面板只负责开关与状态展示，重活（截图、识别、控制）全部跑在后台线程，GUI 主线程保持轻快
- 框架隔离在薄适配层里：若实测内存不达标，可整体替换为更轻的框架（CustomTkinter / Dear PyGui），**业务代码零改动**
- 真正的内存大头是游戏本体与截图/视觉处理，GUI 框架本身的占比很小（百 MB 以内级别）

## 5. 视觉方案与模型训练演进

### 5.1 阶段一：混合识别策略（BetterGI 式，零训练，先跑通）

参考 [BetterGI](https://github.com/babalae/better-genshin-impact) 的三板斧：**固定坐标 + OCR + 少量模板**（它之所以没有大量模板图，就是因为主力是坐标表和 OCR）。跑刀场景对应：

- **固定坐标**：大厅/匹配等 UI 按钮位置固定 → `coord` 策略直接点坐标
- **OCR（RapidOCR）**：识别界面文字（"匹配"、"拾取提示"、物品名），按关键词判断
- **模板匹配**：只用于有特征的图标（撤离点标记等），**不追求"每种物品存模板"**
- **颜色特征**：血条/高亮/加载画面等颜色占比判定

**改动局部化（重要）**：所有识别统一走 `DetectElement` 节点 + `data/elements.json` 元素识别表 —— workflows 只写元素名，识别方式按元素在 JSON 里切换，以后改识别手段（模板→OCR、坐标→模板）只改一行 JSON，**不动流程、不动代码**。

### 5.2 阶段二：YOLO 微调（training/ 文件夹）

**要不要训练文件夹？→ 要，但第二阶段才真正使用。** 现在先建好目录占位。

```
training/
├── dataset/          # 零号大坝游戏内截图 + 标注（YOLO 格式）
│   ├── images/
│   └── labels/
├── configs/          # 训练配置（模型尺寸、超参）
├── scripts/          # 采集截图、导出、转换工具
└── runs/             # 训练产物（权重、日志）
```

**推进顺序（重要）**：

1. 先有**自动化截图能力**（依赖 L0/L1 跑通）
2. 批量采集截图（自动跑图时随手截）→ 筛选去重
3. 标注（labelImg / 在线标注），目标类别：可拾取物品、撤离点、危险区提示等
4. YOLOv8（ultralytics）微调 → 导出 ONNX → 替换 L1 的 `DetectTarget` 实现
5. 验证精度 → 回流补充数据集

> 为什么不是现在训练：训练数据需要先有截图管线；模板匹配 + OCR 足够验证架构价值。先跑通，再优化。

## 6. 跑刀主流程（状态机）

```
大厅 ──▶ 匹配 ──▶ 进场加载 ──▶ 出生点安全确认
                                  │
                    ┌─────────────▼─────────────┐
                    │      搜刮循环              │
                    │ 观察→识别目标→寻路→拾取     │
                    │ →背包/收益检查             │
                    └─────────────┬─────────────┘
             拾取价值下降 │ 背包满 │ 时间到 │ 危险
                            ▼
                     撤离点导航 ──▶ 撤离 ──▶ 结算 ──▶ 循环 / 停止
```

- 状态机是**数据驱动**的（状态定义放配置），StateAgent 维护
- 每个状态 = 一组节点图的入口（比如"搜刮循环"就是一个 L3 任务节点）
- **第一张开发图：零号大坝** —— 点位表、撤离点数据、模板素材均按此图制作

## 7. 安全与合规设计

- **拟人化**：鼠标贝塞尔曲线移动、随机化延迟、操作节奏变化（InputAgent 内置）
- **随机性**：路径、停留点、拾取顺序带随机扰动，避免机械重复
- **紧急停止**：全局热键 + 异常检测（连续失败/状态异常/安全守卫触发）立即停
- **会话限额**：每日运行时长/次数上限（自控，别真挂机一整天）
- **合规红线**：节点库中不提供任何战斗/瞄准能力；拾取只针对普通材料
- **风险意识**：以上手段只降低风险，不保证不被风控；请谨慎、低频使用

## 10. 里程碑规划

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| **M0** | 项目骨架 + 节点引擎核心 + 截图捕获 | 能加载并执行简单 JSON 节点图（截图→匹配→日志），WGC 截图跑通 |
