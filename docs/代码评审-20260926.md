## P1 —— 应尽快修

### 1. 匹配超时的人工确认点是死代码

- 位置：`workflows/enter_match.json:76-84`
- 现象：`after_match_check` 的 `default` 指向 `done`；`match_fail` 没有任何跳转指向它（`end` 仅被 `match_fail` 引用，同为死步骤）。
- 实际行为：匹配 90s 超时后再判一次界面 → 未知界面 → 走 default → 直接打印"进场链路结束（已选干员等待自动开局，或已进入对局）"——**此时干员根本没选**，设计好的 `match_fail` 人工处理暂停永远不会触发。
- 修复建议：`after_match_check.default` 改指 `match_fail`，`match_fail` 改为 `jump_to: wait_match`（人工点完出发回来重等）；或确认 intended 行为后删除两个死步骤。同步补一条链路校验：**没有被任何跳转引用且非入口的步骤应告警**（防再次出现死分支）。

### 2. GUI 会把节点图格式的 demo_smoke.json 当链路"空跑成功"

- 位置：`Gui/WorkflowCatalog.cs:11`（扫全部 `*.json`）→ `Gui/MainForm.cs:86`（进下拉框）→ `ChainCommand.Run`
- 根因：demo_smoke.json 是节点图格式（无 `steps` 字段），`Chain.Steps` 反序列化为空列表（`Data/ChainModels.cs:15` 默认 `new()`）→ `ValidateChain` 空转通过 → 主循环直接跳过 → 打印"🎉 链路执行完成"。**看起来成功，实际什么都没做。**
- 修复建议（二选一，建议都做）：
  1. `ValidateChain` 开头加 `Steps.Count == 0` 报错（一行，兜底所有格式误用）；
  2. `WorkflowCatalog.List` 只列出含 `steps` 成员的链路格式文件（可加一个单测钉住：demo_smoke.json 不应出现在清单里）。

### 3. 窗口最小化不检测，会静默截黑帧乱点

- 位置：`Capture/CaptureService.cs:75-88`（`GetClientScreenRect`）
- 根因：最小化窗口的 `GetClientRect` **仍返回正常客户区尺寸**，只有 `IsIconic` 能判断；现有检查 `if (w <= 0 || h <= 0) return null; // 最小化`（:82）拦不住——注释本身不成立。最小化时 `ClientToScreen` 返回 (-32000,-32000)，BitBlt 戔回黑帧 → 链路在黑帧上继续 OCR/点击。
- 讽刺点：`IsMinimized` 辅助函数和原因注释都在（`CaptureService.cs:139-140`，`GetClientRect 对最小化窗口仍返回正常尺寸，必须用 IsIconic 判断`），只是没接进 `GetClientScreenRect`。
- 修复建议：`GetClientScreenRect` 开头加 `if (IsMinimized(hwnd)) return null;`（一行）。OperatorPicker 已按"返回 null = 最小化"在消费（`OperatorPicker.cs:50-54`），接入后整条链路自动受益。
