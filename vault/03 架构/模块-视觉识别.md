# 模块-视觉识别

> [!info] 一句话
> "看懂屏幕"有四种手段，按**便宜到贵**排：缩略图帧差（2ms）→ 模板匹配（几 ms）→ 区域 OCR（50-90ms）→ 全帧界面识别（600-700ms）；每一层都能独立否决或放行，贵的只在必要时才用。

## 1. 它负责什么、为什么需要它

决策层要的是一个很朴素的问题的答案：**"我现在在哪个界面？这个按钮在哪？"** 但游戏不给任何接口，只能看像素。于是把识别拆成可组合的零件：

| 零件 | 回答什么问题 | 代码 |
|---|---|---|
| `FrameDiff` | 画面动了吗？（动没动是最便宜的信号） | `Vision/FrameDiff.cs` |
| `ChangeGate` | 画面没动，那这一轮还需要真识别吗？ | `Vision/ChangeGate.cs` |
| `TemplateMatcher` | 这个小图（图标/美术字）在画面哪里？ | `Vision/TemplateMatcher.cs` |
| `Ocr` / `OcrTextMatcher` | 画面上有哪些字？有没有我要的词？ | `Vision/Ocr/` |
| `ScreenDetector` | 当前是哪一个界面？ | `Vision/ScreenDetector.cs` |
| `FrameTools.Normalize` | 把任意分辨率拉回 1920×1080 基准 | `Vision/FrameTools.cs` |

为什么这么在意"便宜/贵"？因为一次全界面 `Detect` ≈ **600-700ms**（约 7 次 OCR），而等待界面时画面多数时候一动不动——每 300ms 全量重扫一遍纯属烧 CPU，还会让链路反应变慢。

## 2. OCR：严格层可以裁决，候选层只能报警

引擎是 Windows 自带的 `Windows.Media.Ocr`（`WindowsOcrEngine`），启动时由 `Ocr.Initialize(runtime.ocr_engine)` 装好；`paddle` 选项**尚未接入**，指定了也会回退 windows 并打印警告（`Ocr.cs:11-23`）。

匹配分两层（`OcrTextMatcher.cs:24-82`，这是 ADR #11 的落地）：

| 层 | 判定规则 | 能不能用来点击/判定界面 |
|---|---|---|
| **严格层** | ① 单个识别词**包含**关键词；② 同一行内"最小连续词窗口"拼接后包含关键词（专治 OCR 把"配装"拆成"配"+"装"） | ✅ 可以 |
| **候选层** | 全帧文本里出现了关键词的**任意一个字** | ❌ 只用于提示"你可能和 XX 混淆了" |

严格层还有一个**计数**版本 `CountStrict`（`OcrTextMatcher.cs:85-132`），用于"数一数有几个'未装配'"来判断裸装（`if_ocr` 的 `min_count: 4`）。

分行的规则很土但有效：两个词的垂直重叠 ≥ 较高那个词高度的一半才算同一行（`GroupLines`，`OcrTextMatcher.cs:135-153`），避免密集 HUD 把好几行串成一句。

## 3. 模板匹配：CCoeffNormed + 内存缓存

`TemplateMatcher.Match(frame, templatePath, threshold, region)`：

- 算法 `Cv2.MatchTemplate(..., TemplateMatchModes.CCoeffNormed)`，取最大值位置（`TemplateMatcher.cs:57-59`）；
- 模板按路径缓存在 `ConcurrentDictionary<string, Mat>` 里，循环里不再反复读盘（`TemplateMatcher.cs:10, 77-86`）；
- 实时帧是 BGRA（4 通道）、模板是 BGR（3 通道），自动 `BGRA2BGR` 再匹配；
- 可传 `region = [x,y,w,h]` 只在区域内找（更快更抗干扰），命中坐标会加回区域偏移；
- 模板尺寸 ≥ 搜索区域会直接抛异常（"无法匹配"），这是加载期/诊断期就该发现的问题；
- 返回值 `MatchResult(Found, Confidence, CenterX, CenterY, W, H)`。

阈值惯例：`screens.json` / `elements.json` 里的模板标记基本都写 `0.85`；`annotate` 命令缺省用 0.8。**别把阈值当概率**——NCC 分数对"重复纹理/纯色块"没有分辨力（[[坑-模板零方差假匹配]]、[[知识点-模板匹配与NCC]]）。

## 4. 界面识别：任一标记命中即判定（与老文档不同！）

`ScreenDetector` 的语义（`ScreenDetector.cs:9-12, 33-89`）：

- 遍历 `screens.json`（跳过 `enabled: false` 和 `markers` 为空的），逐条标记算命中：
  - `type: template` → 模板匹配 ≥ `threshold`；
  - `type: ocr` → 严格命中任一关键词；若 `require_all: true` 则要求**区域内所有关键词都命中**（防串台：`配装` 会命中配装界面的"确认配装"，必须连 `出发` 一起要求）；
- **任一标记命中即判定为该界面，置信度取命中标记里的最高值**。这让"主标记 + 兜底标记"的分层自然成立。
- 多界面同时命中时，按 `(置信度, 命中标记数)` 取最优，其余放进 `Alternatives` 让调用方打告警（`Detect`，`ScreenDetector.cs:106-123`）。
- `Scan` 返回按置信度降序的**全部候选**（含未命中的），用于校准阈值和 `mark_unknown` 留证。

两个性能细节：

1. **同帧同区域词表缓存**：一次 `Scan` 内，相同 `region` 的 OCR 只做一次（`wordCache`，`ScreenDetector.cs:36-46`）——否则每个标记各自全帧 OCR，单次 Detect 能拖到十几秒；
2. **分组过滤**：`group` 非空时只扫该组（`lobby` 大厅 / `match` 局内），省一半 OCR（[[决策-局内界面分表group]]）。

区域解析顺序（`ResolveRegion`，`ScreenDetector.cs:127-140`）：显式 `region` 数组 → 否则查 `zones.json` 的 `region_name` → 都没有就全帧搜索，但**同类配置错误只告警一次**（`WarnOnce`），避免每 600ms 刷屏。

> [!warning] 与 `docs/模块说明.md` §5 的冲突
> 文档说"标记**全部**命中才判定为该界面，分数取最差命中置信度"。代码（以及 `screens.json`/`ScreenModels.cs` 的注释）是"**任一**命中即判定，取最高"。README v0.5 也是"任意标记命中 + require_all 防串台"。**以代码为准**。

## 5. 变更门：一次 2ms 的帧差，省掉 600ms 的识别

`ChangeGate`（`Vision/ChangeGate.cs`）在等待界面时决定"这一轮要不要真识别"：

```csharp
using var small = new Mat();
Cv2.Resize(norm, small, new Size(norm.Width/6, norm.Height/6), interpolation: InterpolationFlags.Area);
double diff = prevSmall is null ? double.MaxValue : FrameDiff.Score(prevSmall, small);
if (!gate.ShouldDetect(diff, DateTime.Now.Ticks)) { Thread.Sleep(poll); continue; }
```

- 缩略图 1/6 的帧差约 **2ms**（`ChainCommand.cs:454-466`）；
- 三条兜底：**首轮必扫**、连续跳过 `forceEveryN=5` 轮强制扫、距上次识别超 `maxStaleMs=3000` 强制扫；
- 帧差阈值 `diffThreshold=1.2`（`FrameDiff` 语义：≥3 明显变化、≥0.8 轻微变化）；
- 跳过的次数会计入 `Skipped`，收尾时打印"⚡ 等待 X 期间跳过 N 次重复识别"，让"省了多少"可见。

## 6. 帧归一化与坐标缩放

- `FrameTools.Normalize(frame, designW, designH)`：尺寸已一致就拷贝，否则 `Cv2.Resize`（`FrameTools.cs:9-21`）。**所有模板、所有坐标、所有区域都按 1920×1080 设计分辨率写**。
- 反过来"设计坐标 → 屏幕坐标"由 `CaptureService.MapDesignToScreen` 负责：`屏幕 = 客户区原点 + 设计坐标 × (客户区 / 设计分辨率)`（`CaptureService.cs:93-98`）。点击前必须做这一步，否则窗口化/DPI 缩放下会点偏（[[坑-坐标缩放偏移]]、[[模块-截图与窗口]]）。
- `FrameDiff.Score(a,b)`：`Absdiff` 后取三通道均值（0-255）。尺寸不一致会把 b 缩放到 a（`FrameDiff.cs:12-36`）。

## 7. 耗时账本（真机实测，来自 `docs/模块说明.md` §3）

| 环节 | 实测 | 为什么这么快/慢 |
|---|---|---|
| 可通行性模型推理 | ~0.9ms | 112×224 小图 + ONNX 原生运行时（DirectML） |
| 全帧 OCR | ~114ms | Windows OCR + 预处理（灰度/反色/Otsu/BMP 编解码） |
| 区域 OCR（800×400 / 240×80） | ~89ms / ~54ms | 固定开销占大头（几千像素也要 ~50ms） |
| 单次全界面 Detect | ~600-700ms | 约 7 次 OCR + 若干模板；靠变更门避免重复扫描 |
| 1/6 缩略图帧差 | ~2ms | 320×180 的均值差 |

结论：**能不用 OCR 就不用**。能用模板就用模板，能用区域就别全帧，能靠帧差跳过就跳过。

## 8. 当前缺口

| 项 | 状态 |
|---|---|
| `color` 类型标记 / 元素策略 | 代码里只有注释"待实现"，`ElementParams` 已预留 `r/g/b/tolerance/min_ratio` |
| Paddle OCR | 未接入，`ocr_engine: paddle` 会回退 windows |
| OCR 引擎初始化时机 | CLI/GUI 启动时初始化一次；单测里需要手动 `Ocr.Initialize` 或跳过 |
| `annotate` 对 ocr 策略 | 不支持（只支持 coord/template），要验证 ocr 元素请用 `ocr` 命令 |
