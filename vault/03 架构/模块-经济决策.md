# 模块-经济决策

> [!info] 一句话
> "这个东西要不要捡、背包满了丢什么、什么时候该撤"——三句话，写成三个**纯函数**：不读文件、不用随机数、不记状态，给同样的输入永远得到同样的输出，所以能用单元测试钉死。

## 1. 它负责什么、为什么需要它

局内真正要连续决策的其实只有三件事：

1. **捡不捡**（`ShouldPick`）
2. **满了丢什么**（`ShouldDiscard`）
3. **该不该撤**（`TimeToExtract`）

把它们从"感知"和"移动"里剥出来单独写，是为了**能在没有游戏的情况下判断对错**：给一个假物品库 + 一句假的 OCR 读数 + 一个背包状态，断言结果。伺服/输入那些东西必须上真机，但这三条规则不用。

> [!warning] 现状：只有骨架 + 单测，**没有任何搜刮代码调用它**
> 这是刻意的红线：**K1（撤离链路）跑通前不写任何搜刮代码**。现在这些函数是 S0 阶段的产物——定义清楚"决策长什么样"，等 K2 再来接线（[[决策-红线与边界]]、`docs/跑刀工程提案.md` §5/§8）。

## 2. 四个函数

### 2.1 `TierValue(tier)`：品质文字 → 数字

```csharp
"白"=>1, "绿"=>2, "蓝"=>3, "紫"=>4, "金"=>5, "红"=>6, 其它(含 null/空)=>0
```

数字只用于**比较大小**，不是价值。品质在游戏里的表现是**格子背景色**（[[坑-容器类别定义]] 里有颜色样本标定的记录），所以 0 的语义是"没认出来"——认不出来就别当高价值处理。

### 2.2 `MatchItem(catalog, ocrText)`：OCR 读数对物品库

匹配方向很重要：

```
OCR 读数是"长文本"（带噪声/后缀，如 "战术背包x1"、"9MM弹药"）
物品库里的 name / ocr_keywords 是"短词"
→ 判定 t.Contains(短词)，不区分大小写
```

- 先比 `name`，再比 `ocr_keywords[]` 里的每个变体；
- 命中多条时**返回第一条**——"录入顺序即优先顺序"，这是数据表里能人为控制的优先级；
- 空白读数直接返回 null（不猜）。

### 2.3 `ShouldPick(catalog, ocrText, tierValue, backpackFull)`

四个条件**全部满足**才捡：

| 条件 | 为什么 |
|---|---|
| 物品库有条目命中 | 没命中 = 不认识 = 不捡（fail-open：跑刀宁可漏捡，不可乱捡） |
| `entry.pick == true` | 白名单起步：不是"有价值就捡"，而是"我明确想要才捡" |
| `tierValue >= max(1, catalog.min_tier_to_pick)` | 品质门槛，`min_tier_to_pick` 现在是 2（绿） |
| `!backpackFull` | 没地方放就别捡 |

### 2.4 `ShouldDiscard(tierValue, keepTier)` 与 `TimeToExtract(...)`

- `ShouldDiscard`：`tierValue < keepTier` → 丢。规则极简（"背包满时品质低于保留档就丢"），真正细化留到 K3。
- `TimeToExtract(remainingMinutes, backpackFull, extractDeadlineMin)`：
  - `backpackFull` → 撤（装满了就别恋战）；
  - `extractDeadlineMin > 0 && remainingMinutes <= extractDeadlineMin` → 撤（撞时间红线）；
  - `extractDeadlineMin = 0` → 时间红线**禁用**（现在的配置就是 0）。

## 3. 数据从哪来：`data/item_catalog.json`

| 字段 | 现值 | 说明 |
|---|---|---|
| `items[]` | **空数组** | 增量录入：打游戏看到什么录什么 |
| `min_tier_to_pick` | 2 | 局内拾取最低品质档（白1…红6） |
| `extract_deadline_min` | 0 | 撤离时间红线，0=禁用 |

条目字段（`ItemCatalogModels.cs:28-64`）：`name`（OCR 主关键词）、`ocr_keywords[]`（变体）、`type`（长枪/手枪/头盔/护甲/胸挂/背包/药品/弹药/材料…）、`tier`（白绿蓝紫金红）、`grid_w/grid_h`（占格）、`value`（哈夫币）、`pick`（是否值得捡）、`note`。

> [!warning] 与提案的一处不一致
> `docs/跑刀工程提案.md` §4 曾计划加 `priority`（背包/胸挂最高）与 `quality_keep`（丢弃阈值）两个字段；实际落地的是 `min_tier_to_pick` + `extract_deadline_min` 两个表级门槛 + 条目级 `pick`，**没有** `priority` / `quality_keep`。以代码为准；将来要做"按优先级决定丢谁"时再补。

## 4. 为什么坚持"纯函数"

| 好处 | 具体体现 |
|---|---|
| 可测 | `EconomyAgentTests` 覆盖：品质映射、包含匹配/大小写/空白、背包满、品质不达标、白名单外、无条目、丢弃边界、撤离红线 |
| 可换策略 | 现在是白名单，将来换成价值函数只改实现，调用方不用动 |
| 不会半夜作妖 | 没有 IO、没有随机、没有隐藏状态——同样的输入永远同样的输出，出问题一定是规则写错了 |

代价是：所有"上下文"都得从参数传进来（`backpackFull` 这种布尔值也是外面算好再传）。这让调用方多写几行，但决策逻辑本身变得极其好读。

## 5. 接线时要补什么（K2 的事）

- [ ] 背包容量/剩余格数怎么读（OCR？格子计数？）——`backpackFull` 的来源

- [ ] 何时调用（搜刮伺服的 `loot_roam`，见 [[模块-伺服循环]] 的 follow_marker 同级设计）

## 6. 与仓库机制的关系（背景知识）

拾取决策依赖几条真机机制（`docs/仓库交互手册.md`）：

- 品质 = **格子背景色**（白/绿/蓝/紫/金/红）；
- 容量：裸装 5 个单格口袋 + 安全箱（新手 2 格）；固定装备槽长枪×2、手枪×1、头盔、防弹衣、胸挂、背包各 1；胸挂/背包有**物品类型限制**（不是什么都能塞）；
- 转移：仓库→身上左键双击（自动化首选）；身上→仓库悬停+`Ctrl+F` 或 `Ctrl+左键`。

这些现在都只是"知识存档"，代码未实现（`docs/仓库交互手册.md` 标题就写着"代码未实现"）。

## 7. 常见误解

| 误解 | 事实 |
|---|---|
| "有价值就捡" | 现在是白名单起步，`pick` 必须显式为 true |
| "认不出来就按最高价处理" | 认不出来 `TierValue=0`、`MatchItem=null` → **不捡** |
| "撤离红线一直生效" | `extract_deadline_min = 0` 表示**禁用**，只有背包满会触发撤离 |
| "这些函数已经在跑刀了" | 没有。只有单测在调用它们 |
