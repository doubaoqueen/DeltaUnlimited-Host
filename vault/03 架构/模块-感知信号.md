# 模块-感知信号

> [!info] 一句话
> "被打了一枪"和"前面有个金箱子"这两件事，不需要神经网络也能看出来——**边缘区域红色像素突然变多**就是受击红屏，**准星附近金色/紫色像素占比升高**就是光柱；这里把它做成两个廉价判定器，阈值每次重新随机取。

## 1. 它负责什么、为什么需要它

局内有几类信号，用规则就够，训练模型反而亏：

| 信号 | 为什么规则就够 | 成本 |
|---|---|---|
| 受击红屏 | 屏幕边缘整片变红，占比变化非常显著 | 颜色统计，1-2ms |
| 物资光柱（金/紫） | 颜色极纯、位置集中在准星附近 | HSV 占比，1-2ms |
| 卡墙/低效移动 | 帧差双守卫（已在 `patrol` 验证） | 帧差，1-2ms |

它们的共同点是：**不需要"理解"画面**，只需要"数某颜色占了多少"。好处是零训练、零标注、失败可解释；坏处是阈值必须现场标定（显卡色彩设置/亮度会偏色）。

> [!warning] 当前状态：只有骨架，没有接线
> `RatioDetector` / `LootGlow` / `DefaultSignals` 目前**只被单元测试使用**，没有任何命令或链路调用它们；所有阈值都是"待 K0 标定的占位值"。真正的接线要等危险场景标定完成（[[标定-危险信号阈值]]）。

## 2. SignalSpec：每个信号必须写清的五件事

`SignalSpec`（`Signals.cs:6-28`）是这张表将来的行格式，五项缺一不可：

| 字段 | 含义 | 例子（受击红屏） |
|---|---|---|
| `Name` | 信号名 | `hit_flash` |
| `Region` | 检测区域（`zones.json` 具名区或矩形） | `zone_left_mid, zone_right_mid`（屏幕两侧边缘条） |
| `ThresholdMin` / `ThresholdMax` | 阈值**随机范围**（铁律：生产永远在该范围内取样，不得用固定值） | 0.18 - 0.30 |
| `ConfirmFrames` | 连续 N 帧确认（防误触） | 3 |
| `Fallback` | 触发后的失败回落 | `AbortToPause 人工接管（不自动逃跑）` |
| `Source` | 真机出处（哪一局、什么画面标的） | 待 K0 标定（`docs/K0采集清单.md` §6.1） |

为什么阈值要随机？因为"每次都卡在 0.24 触发"本身就是一种可识别的机械特征；随机范围还顺带防止"同一个阈值反复误触"。

## 3. RatioDetector：一个单通道判定器

`RatioDetector`（`Signals.cs:33-84`）只做一件事：喂入"某个统计量"（红色占比、金色占比…），返回"是否触发"。

```
构造：threshold = Sample()                        // 在 [min,max] 里随机取一个
Update(ratio):
    ratio >= threshold → run++；run >= ConfirmFrames → run=0, threshold=Sample(), return true
    ratio <  threshold → run = 0, return false
Reset(): run=0, threshold=Sample()                // 换局/进新场景时人工复位
```

要点：

- **每次触发后重新取样阈值**（"随机范围铁律 + 防同阈值反复误触"）；
- 计数是**连续**的：中间断一帧就清零（`else _run = 0`）；
- 纯逻辑，`Random` 注入即可单测（`tests/DU.Tests/SignalsTests.cs` 覆盖了触发/不触发/中断清零/复位重取样）。

## 4. LootGlow：金/紫双通道

`LootGlow`（`Signals.cs:88-112`）包两个 `RatioDetector`（金、紫），`Update(goldRatio, purpleRatio)` **任一通道达标即触发**，`Reset()` 同时复位两路。

两通道而不是一个，是因为物资等级不同、颜色不同，而且紫色光柱更稀少——分开计数才能分别标定阈值。

## 5. 默认五要素（占位值，全部待标定）

`DefaultSignals`（`Signals.cs:116-153`）：

| 信号 | 区域 | 阈值范围 | 确认帧 | 回落 |
|---|---|---|---|---|
| `hit_flash`（受击红屏） | `zone_left_mid,zone_right_mid`（两侧边缘条） | 0.18 - 0.30 | 3 | `AbortToPause 人工接管（不自动逃跑）` |
| `loot_glow_gold`（金光柱） | 准星附近 ROI | 0.05 - 0.12 | 3 | 不触发走近子流程（错过不亏，误触才亏） |
| `loot_glow_purple`（紫光柱） | 准星附近 ROI | 0.03 - 0.08 | 3 | 不触发走近子流程 |

对应的具名区域在 `data/zones.json` 里确实存在：`zone_left_mid = [0,350,450,200]`、`zone_right_mid = [1200,540,720,180]`（设计分辨率）。

## 6. 缺的那一半：谁去数颜色？

这两个判定器**只做判定，不做统计**——注释写得很明确："HSV 颜色统计由捕获层算好占比后喂进来"（`Signals.cs:86-87`）。

也就是说现在还缺一层实现：

```
截图 → 取 ROI → 转 HSV → 按色相/饱和度/亮度区间数像素 → 占比 → 喂给 RatioDetector
```

这层没有写在任何现有类里（`Capture/` 只负责截图，`Vision/` 里没有颜色统计器）。❓待确认：是放进 `CaptureService` 之后新增一个 `Vision/Signals` 里的统计器，还是在调用方（`patrol`/`follow_marker`）里现算。按"每周期预算"的规划（廉价档 1-2ms），应该做成一个纯函数放进 `Vision/`。

## 7. 为什么要"连续 N 帧 + 人工接管"

- **连续 N 帧**：单帧误判太多——血条闪一下、屏幕特效、UI 弹窗都可能让红色占比跳一下；3 帧约等于"持续了 1-2 个伺服周期"。
- **触发后人工接管**：受击意味着"附近有人"，这时自动逃跑/自动反击既违反项目红线（不做战斗），也容易把角色送进更糟的位置。所以 `Fallback` 写的是 `AbortToPause`——**停下来交给人**（[[决策-红线与边界]]）。

## 8. 落地计划（按优先级）

- [ ] 颜色统计器（ROI → HSV 占比）——先做红屏，最简单
- [ ] K0 采一批受击/光柱样本，标定阈值范围与区域（[[标定-危险信号阈值]]）
- [ ] 迁入数据表：`data/signals.json`（或 `runtime.json` 的 `signals` 段）——注释里已经写明这个去向
- [ ] 接线到 `patrol` / `follow_marker`：触发 → `Escalate` 或 `AbortToPause`
- [ ] 声音感知（WASAPI 回环）已立项但**暂不投入**，见 [[决策-声音感知立项未投入]]
