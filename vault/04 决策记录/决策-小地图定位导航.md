# 决策：用圆形小地图做地形匹配定位

> [!info] 一句话
> 把屏幕上左上角那块**圆形小地图**，拿去和官方 4096×3072 大地图做"地形匹配"（归一化互相关），算出"我现在在底图的第几个像素"——**全程只看屏幕，不读内存、不注入**。这是"计划路线"能落地的地基。

## 一、为什么非要有定位

K1（撤离直通）原本的路子很朴素：HUD 上出现撤离点标记 → 让标记居中 → 往前走。

问题在于这条路**只知道方向，不知道位置**：

- 走偏了不知道（标记还在屏幕右边，但你已经绕进楼里了）；
- 被墙挡住不知道该往左还是往右；
- 更关键的是——2026-10-21 用户决定允许"出生点 → 撤离点"的计划路线，**没有位置，路线表就是废纸**（不知道自己在路线的哪一段，怎么执行？）。

所以定位不是一个"锦上添花的功能"，它是**路线方案的前置闸门**。

## 二、方案：地形匹配（不是识别图标）

1. 取左上角圆形小地图面板（用户口述四点定圆：圆心 ≈(165,185)、半径 ≈120-129px，1920×1080 帧坐标）；
2. 用**圆形掩膜**只取圆内像素，把圆外填成模板均值，压掉 HUD 边角干扰；
3. **多尺度**搜索：把小地图缩放到 150-440px，在 4096×3072 底图上滑窗匹配；
4. 打分用 **NCC（归一化互相关）**：光照/亮度变化不影响，看的是"纹理形状像不像"；
5. 取**最高分**的尺度与位置（**不按票数投票**——小尺度会在纯色区扎堆，投出来是错的）。

> [!note] 术语：NCC（归一化互相关）
> 一种"两块图有多像"的算法，输出 -1 到 1，越接近 1 越像。它对整体亮度/对比度不敏感，所以游戏里开灯关灯、昼夜变化影响较小（原理见 [[知识点-模板匹配与NCC]]）。

工程上加速靠三件事：FFT 算互相关、积分图算局部方差、**低方差区域屏蔽**（纯色区和哪都像，直接不算）。

## 三、素材与坐标换算

| 素材 | 来源 |
|---|---|
| 官方零号大坝底图 4096×3072 | 官网地图工具瓦片 `img/map_db/4_{x}_{y}.jpg` 拼接（188/192 块，缺的 4 块在边界外） |
| 官方标记 1423 条（物资点） | 同站 `map_article.js`（含世界坐标 x/y、图标、大区域、条件） |
| 坐标换算公式 | 同站 `main.js` 的 `getMapPos`/`getSourceMapPos` |

换算结果验证：1423 条标记里 **1422 条落在图内**，说明公式与底图对得上。这一步很重要——**没有可信的"像素 ↔ 世界坐标"换算，定位出来的点就没法变成"往哪走"**。

## 四、P0 验证：先"能不能"，再"准不准"

| 阶段 | 结果 |
|---|---|
| 首批 3 帧 | 用户肉眼确认 **3/3 命中** |
| 批量 8 组复核（2026-10-21） | 4 对 / 2 错（m1a 存疑、m2d 未评） |
| m2a 改判 | 轨迹显示它与用户确认正确的 m2b 在同一条平滑轨迹上（20 秒位移 170px ≈ 3.2 m/s）→ 用户复核"完全匹配"，改判正确 |
| m1a 复核 | 用户确认正确 |
| m2d | **不是小地图**（Tab 背包全屏），由 HUD 状态门处理，不参与定位回归 |
| **当前回归集** | **m1a / m1b / m1c / m1d / m2a / m2b = 6 对 0 错** |

另外两个重要的"诚实"结论：

- **分数不能当置信度**：有一帧 **0.904 高分却是错的**。所以定位结果必须再过轨迹过滤；
- **C# 与 Python 实现等价**：6 个标注样本位置逐像素相同。C# 的 `CCOEFF_NORMED` 分数比 Python 掩膜 NCC 低约 0.1-0.2，所以 `MinScore` 默认 0.50（最弱命中样本 0.515@380）。

## 五、三个坑，三道防线

### 坑 1：UI 面板会盖住小地图

逐帧定位 00:28:20-00:30:30 时发现，00:30:28 出现 **2 秒瞬移 1394px（≈265 m/s）**。查该帧 OCR：屏幕上是"破坏物资室铁门 / 行动地点：水泥厂 / 报酬 30000 / 进行行动"——**行动接取站面板**盖在了小地图上。

结论：**交互 UI 面板会污染小地图区域，此时 NCC 仍给 0.6+ 分但位置全错。**

### 坑 2：第一帧就锚错了

首帧（00:28:21，0.520 分）被直接采信为锚点，随后 25 帧候选全部"远离它"、被判超速拒绝。真相是**锚点本身错了**。

### 坑 3：Tab 背包里根本没有小地图

用户复核第 8 组时指出："完全错误，左边甚至不是小地图，我估计是我打开的背包键时的界面"。定位器把背包 UI 纹理当成小地图，得到 0.648@180 的"高分错误位置"。

### 防线 1：轨迹过滤（`LocalizerTrack`）

| 规则 | 做法 |
|---|---|
| **双帧首锚** | 首帧候选先挂起，第二帧候选与它一致（≤120px）才锁定 |
| **速度门** | 只接受相对上次确认位置速度 ≤30px/s 的候选；长空档按 30s 封顶，防"放大器"式瞬移 |
| **重锚定** | 连续 3 帧被拒、但候选彼此一致（≤100px）→ 判定锚点漂了，重新锚定并报告 |

效果（同一段 67 帧）：修复前 40 接受 / 27 沿用（错误首锚导致连续误拒）；修复后 **60 接受 / 4 沿用**（4 帧全是真实误定位：1 帧无结果 + 3 帧 UI 遮挡/瞬移）。轨迹速度 median 4.0 m/s、p90 7.2、max 11.9——冲刺量级，合理。

### 防线 2：HUD 状态门（`HudStateGate`）

定位前先用**局内界面表**（`screens.json` 的 `group=match`）识别当前帧；命中 `match_backpack` / `match_map` / `match_settlement_*` 就判定"没有小地图"，直接跳过定位。识别不到界面时 **fail-open**（当正常 HUD 处理），交给轨迹过滤兜底。

顺带修了 `match_backpack` 的关键词：原来 `剩余离` 常被 OCR 读成"刺余/离阎"，严格匹配不稳，改成 `本局收获 + 胸挂 + 背包` 三词齐备。

### 防线 3：`match_backpack` 兼作状态门输入

分表不只是"省 OCR"——它让"这一帧有没有小地图"变成一个**可以查表回答**的问题（见 [[决策-局内界面分表group]]）。

## 六、两局全量验证（2026-10-21 深夜，用户亲自跑）

| 局 | 时长 | 帧数 | 接受 | 无定位 | 超速拒 | UI 跳过 | 接受帧最大间隔 | 速度中位/p90/最大 |
|---|---|---|---|---|---|---|---|---|
| 常规局 | 616s | 313 | **220（70%）** | 59 | 24 | 9 | **27s** | 4.37 / 7.59 / 46.92 m/s |
| 机密局 | 766s | 391 | **211（54%）** | 134 | 20 | 25 | 77s | 0.89 / 5.22 / 19.49 m/s |

**拒绝不是随机散布的**，聚类后每一段都能解释：

1. **刚落地**（机密局 00:28:26-00:29:22 连续 31 帧无定位）——部署动画/小地图还没画出来；
2. **开 UI 前后**（开地图 00:32:52、开背包 00:34:31 等）——UI 帧被状态门挡下，其前后几帧小地图被遮挡；
3. **室内/地下**（00:33:54-00:34:17 等）——小地图显示室内平面图，和室外底图不匹配（**已知局限**）；
4. **少量瞬移误报**（超速拒 24+20 帧）——过滤生效；常规局最大 46.92 m/s 是 30s 空档下漏过的一次误接受，属待改进。

结论：**轨迹可用**（常规局接受帧最大间隔 27s，没有 >30s 的空档；机密局的 77s 空档来自长时间开背包搜刮，符合预期）。

## 七、实时化：先验局部搜索

离线能跑不代表能用：纯 Python 多尺度一帧要数秒，8Hz 需要毫秒级。

第一步是 **`LocalizePrior` 先验搜索**：只在上帧位置附近的窗口 + 相邻 3 个尺度里搜，而不是全图 8 尺度扫描。预期大幅提速，同时进一步压低误报。

> [!warning] 实时化还没完成
> 实时链路要 C# + 降分辨率 + 限制搜索窗口三者一起上；目前只做到"先验缩小搜索范围"。8Hz 能不能稳住 ❓待确认（需要用真机帧压测）。

## 八、分层/室内地图（2026-10-22 挖通，待投入）

用户点出"室内/地下的小地图不一样"，于是把官网的分层数据也挖了下来：

| 图层 | 含义 | 瓦片 | 拼接结果 |
|---|---|---|---|
| `map_db` | 室外主图（P0 用的就是它） | 16×12 × 256px | 4096×3072 |
| `daba_0f` | 地下通道（B1） | 8×8 × 512px | 4096×4096 |
| `daba_1f` | 行政辖区 1F | 8×8 × 512px | 4096×4096 |
| `daba_2f` | 行政辖区 2F | 8×8 × 512px | 4096×4096 |

首轮室内验证：室内帧对楼层图**确实能匹配**（分数 0.51-0.74，室外图同帧多为"无定位"），**但三个楼层的得分几乎相同**（例：00:37:14 三层都是 0.736；00:34:00 分别是 0.530/0.566/0.607）——**当前判不出自己在几层**。

待办四条：楼层判别信号（小地图上的 B1/1F/2F 字样？各层独有地形？时序先验）、多图层定位器（先判层再定位，或全层扫描看分差 margin）、楼层坐标系标定（`bj=64` 与室外 `bj=128` 不同）、室内外切换点（门/楼梯）标定。
