# 决策：双引擎架构（chain + 伺服）

> [!info] 一句话
> 界面上的事（识别界面、点按钮、等下一屏）交给 **2Hz 的 chain 引擎**；对局里走路的事（转向、冲刺、停）交给 **8Hz 的伺服循环**。两者不是竞争关系，是**分工**：chain 调一次伺服，伺服干完活把结果交回来。

## 一、为什么不能一个引擎干两件事

| 维度 | 界面流转（chain） | 走位（伺服） |
|---|---|---|
| 关心什么 | "现在是哪个界面？该点哪个按钮？" | "目标在我左边多少度？该转多少？" |
| 天然频率 | **2Hz** 左右（一次全界面识别 `Detect` 实测 600-700ms） | **5-10Hz**（125ms 一拍，8Hz 起步） |
| 单次代价 | 一次识别 ~7 次 OCR，很贵 | 一帧模板匹配 5-10ms + 颜色统计 1-2ms，很便宜 |
| 出错后果 | 点错按钮 → 卡在某个界面（可恢复） | 转过头/没停住 → 撞墙、掉沟、暴露（不可恢复） |
| 能不能有人确认 | 能：每个异常点可以 `pause` 等回车 | 不能：走路中间不能等人 |

结论很简单：**2Hz 的轮询撑不起移动**。你不可能每 500ms 才决定一次"往哪转"，那是醉汉走位。反过来，用 8Hz 的紧循环去轮询"现在是不是结算界面"，会把 CPU 全烧在 OCR 上。

## 二、chain 引擎：界面流转的"脚本解释器"

chain 读一份 JSON（`workflows/enter_match.json`），按 `steps` 顺序执行，每一步是一个 `op`：

- `click_element`：点某个元素（点完必须验证目标界面出现，失败重试）；
- `switch_screen`：截一帧、识别一次、按 `branches` 表分流（这是 v7 的核心，把 12 个 `if_screen` 合成一步）；
- `wait_screen`：轮询等界面出现/消失；
- `pause`：人工确认点；
- `mark_unknown`：认不出的界面 → 截图 + OCR 词表留证，然后交人工。

它的价值是"**把流程变成数据**"：改流程改 JSON，不改代码。进场链路从 v1 走到 v7，一直是这个模式。

## 三、伺服循环：走位的"肌肉记忆"

伺服（servo）就是"看一眼 → 算一下 → 动一下"的高频小闭环。代码在 `Vision/Servo/ServoLoop.cs`，每周期做四件事：

1. **先查急停**（`CommandUtil.StopRequested`）——任何一拍都可以被按停；
2. **感知**：取一帧，算出目标标记的偏移量、距离、帧差（画面变化量）；
3. **决策**：`ServoController.Decide` 是纯函数——比例控制 + 死区 + 随机抖动，输出"转多少 + 冲不冲"；
4. **动作**：`ServoAction` 只允许三种——转向、冲刺、停（Idle）。

它内置五道收尾判据，不需要外部催它停：

| 判据 | 触发条件 | 结局 |
|---|---|---|
| 急停 | 每周期都查 | `Stopped`（急停/人工中止） |
| 到达 | 距离 ≤ `arrive_meters`（默认 12m） | `Success` |
| 卡死 | 连续 3 个周期帧差 < 4.0（贴墙了） | `Stuck` |
| 危险 | 可通行性预警连续 10 个周期仍 blocked | `Danger`（交人工，**不自动绕行**） |
| 超时/上限 | 180s 或 10000 周期 | `Timeout` |

> [!note] 术语：伺服
> 原意是"伺服电机"——不停根据反馈微调。这里指"用画面反馈不停微调动作"的循环，和 chain 的"一步一步走流程"正好相反。

## 四、怎么接：op 薄壳

chain 不能自己走位，伺服也不该懂"界面"。所以中间加一层**薄壳**：一个 op 名字，内部同步跑完一轮伺服，把结果交回 chain。

```jsonc
// 示意（不是现有文件内容）
{ "op": "follow_marker", "desc": "跟随 HUD 导航标记去撤离点" }
```

`follow_marker` 的壳（`Vision/Servo/FollowMarkerOp.cs`）只有三件职责：

1. **接线**：把感知器、动作器、停止检查注入 `ServoLoop`；
2. **兜底**：`try/finally` 里一定 `Release()`，无论成功、超时、急停、异常都不留按住的键；
3. **交结果**：把 `ServoResult` 还给 chain，chain 按 JSON 里的分支决定下一步（成功→继续撤离流程；超时→重试/交人工；危险→暂停）。

第二个 op `loot_roam`（随机漫游 + 交互提示扫描）是 K2 的事，现在只有设计没有实现。

> [!important] op 薄壳的意义
> chain **永远不知道**"伺服怎么转的"，伺服**永远不知道**"现在在哪个界面"。两边各自可单测：伺服用假感知器就能跑（`FollowMarkerOpTests` 就是这么测的）。

## 五、线程模型：为什么不开新线程

伺服**跑在链路线程内，同步阻塞**。

- 如果另起线程：链路线程在等伺服结果的同时，可能又来一次识别/点击 → 键鼠输入打架；GUI 还要处理两个线程的急停与状态；
- 同步执行的代价只是"链路卡在这里"，而链路线程本来就是后台 `Task`，**GUI 不会卡**；
- 急停天然贯穿：链路线程里的 `StopRequested` 一样能被 GUI 按钮置上。

一句话：**用一个线程换掉一整类并发 bug**。

## 六、每周期能干什么：预算表

| 档位 | 内容 | 耗时 | 什么时候用 |
|---|---|---|---|
| 廉价（每周期可算） | 全帧截取 30-50ms、ROI 模板匹配 5-10ms、颜色统计 1-2ms、帧差 1-2ms | 约 40-65ms | 每拍 |
| 中等（按需，~2Hz） | 区域 OCR 150-250ms | 0.15-0.25s | 需要读字（距离数字、交互提示文字） |
| 昂贵（事件触发） | 全帧 OCR / 全图搜索 | 数百 ms | 只在未知界面 dump、标定诊断 |

8Hz = 每拍 125ms。cheap 档刚好塞得下，OCR 只能隔几拍做一次——这就是为什么"伺服不能靠 OCR 活"。

## 七、两类风险不混在一起

这是双引擎最容易被忽略的好处：

- **移动的风险**（撞墙、走错、暴露）→ 靠"急停检查 + 每周期最大动作量钳制"，伺服里解决；
- **点击的风险**（点歪、点到别的按钮）→ 靠"落点校验 + fail-open 放弃点击"，chain 里解决（见 [[坑-ClickAt点到光标位置]]）。

> [!warning] 铁律：伺服周期内禁止点击
> 需要点击时（开门、按 F 撤离）**退回 chain 层**，走 `ClickAt` 的落点校验。移动永远有急停，点击永远有校验——两者不混在同一个循环里。

## 八、代价与限制

- **伺服会阻塞链路**：一轮最长 180s，期间链路什么都不做（这是故意的，但意味着"伺服卡住 = 整个链路卡住"）；
- **伺服的感知还没真机标定**：`TemplateMarkerPerceiver` 的位置有了，导航标记的多模板要 K0 素材补；
- **频率不是越高越好**：8Hz 是"够跟标记又不显得机械"的折中，真机标定后可调；
- **两套参数都要随机**：`runtime.json → servo` 里增益 0.35-0.55、死区 40px、每周期最大转向 260px、抖动 12px 全是范围——固定值会让走位看起来像机器（见 [[决策-会话限额与风控]]）。
