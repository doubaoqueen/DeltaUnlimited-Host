# 决策：会话限额与风控

> [!info] 一句话
> 默认**每日累计自动化 240 分钟（4 小时）**、局数上限默认不限（`0`）；比这两个数字更重要的是背后的铁律——**所有拟人化参数必须是随机范围，禁止固定值**。限额不是技术限制，是给"辅助"这个词划的界。

## 一、限额参数

`data/runtime.json`：

```jsonc
"session_limits": {
  "max_minutes_per_day": 240,   // 每日累计自动化时长上限（分钟），0 = 不限
  "max_matches_per_day": 0      // 每日自动化局数上限，0 = 不限
}
```

| 参数 | 默认 | 含义 | 取值理由 |
|---|---|---|---|
| `max_minutes_per_day` | **240** | 一天累计跑多久就停 | 4 小时。文档没写为什么取这个数，能读出的是"把整天挂机压成最多半天" |
| `max_matches_per_day` | 0 | 一天最多几局；0 = 不限 | 文档没写理由；先用时长做唯一约束，局数不额外卡 |

设计意图写在代码注释里：**防"挂机一整天"这类最容易被风控、也最违反项目初衷的用法**。

> [!warning] 现状提示（❓待确认）
> 参数与数据模型已就位（`RuntimeModels.SessionLimits`，缺失时默认 240），但截至撰写时在代码里**没有检索到计时与"到限自动停"的执行点**——也就是说限额目前更像"写在纸上的自律"，还没变成程序强制。这一项需要确认是否尚未接线。

## 二、为什么"限额"本身就是保护

很多人会把限额理解成"限制功能"，其实它保护的是三件事：

1. **保护账号**。风控看的是行为模式，不是单次动作。一个账号每天精确地在线 12 小时、路线固定、操作节奏恒定——这本身就是最显眼的特征。限额把总暴露时间压下来。
2. **保护项目性质**。这个项目的定位是"帮人做重复劳动"，不是"替人上班"。一旦每天挂满，它就从"助手"变成"外挂式产出"，红线②的意义也会跟着塌。
3. **保护注意力**。限额逼着人回来接手、看日志、发现问题。K1-K5 全部是"人盯"形态，限额是这条纪律的技术化表达。

## 三、参数全随机：比限额更硬的铁律

2026-09-22 有一条专门的提交把这句话入库：**拟人化参数必须保持随机范围，禁止固定值**。

原因是机械感的来源不是"动作像不像人"，而是**节奏的规律性**。固定延迟 = 高精度定时器 = 一眼假；随机范围 = 每次都不一样 = 像人在犹豫、看屏幕、手滑。

现有参数（全部是范围）：

| 组 | 参数 | 值 |
|---|---|---|
| 点击停顿 | `click_pause_min/max` | 150-320 ms |
| 按压时长 | `press_hold_min/max` | 100-220 ms |
| 按键短按 | `key_tap_min/max` | 35-90 ms |
| 组合键间隔 | `key_gap_min/max` | 15-30 ms |
| 鼠标移动 | `mouse_step_delay` / 缓动步数 / 抖动 | 3-11 ms / 随机步数 / 系数 0.8-1.2 |
| 鼠标轨迹 | 弧线最大偏移 / 逐点抖动 / 过冲 | 90px / 2px / 概率 0.18、5-22px |
| 伺服（局内走位） | 转向增益 / 死区 / 每周期最大转向 / 抖动 | 0.35-0.55 / 40px / 260px / 12px |

> [!important] 铁律的边界
> "随机"不等于"乱"：**范围是标定出来的**（比如转向增益要配合 `px_per_90deg`），随机只发生在范围内部。把范围改成固定值，等于把标定结果变成机械节拍。

## 四、低频 + 人在场

限额之外还有两条软约束：

- **低频**：跑刀自动化的单局节奏远慢于真人高手是**正常的**，不追求极限速度。想"跑得比人快"这个念头本身就该被否掉；
- **人必须在场**：K1-K5 全部人盯；GUI 有急停按钮（按钮 / Ctrl+C / 暂停面板"中止"三路同源）、有暂停面板、有托盘气泡通知。

## 五、风险自担

> [!danger] 说清楚，不留幻想
> 拟人化、限额、低频、人在场，全都只是**降低**被风控识别的概率，**不保证**不被识别。任何游戏自动化都可能违反用户协议、导致封号。项目文档在 README、项目大纲、跑刀方案三处都写了这句，不是免责套话。
