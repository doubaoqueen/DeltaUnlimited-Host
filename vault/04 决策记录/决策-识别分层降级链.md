# 决策：识别分层降级链（OCR → 模板 → 坐标 → 人工）

> [!info] 一句话
> 每次要回答"现在是什么界面 / 这个按钮在哪"，程序都按固定顺序试：**OCR 严格命中 → 模板匹配 → 坐标直点 → 停下来问人**。越靠前越灵活但越慢，越靠后越脆但越省事。

## 一、这条链长什么样

```
① OCR 严格层命中（完整关键词；同一行里被拆开的词会先拼起来再比）——命中才允许行动
        ↓ 没命中
② 模板匹配（NCC 相似度 ≥ 阈值，一般 0.85）
        ↓ 没命中
③ 坐标直点（标定时记下的固定位置）
        ↓ 仍然不对
④ 人工：pause 等回车 / mark_unknown 留证
```

> [!note] 术语：降级链
> 不是"备用方案随便挑一个"，而是**有顺序、有条件的兜底**：高优先级手段失败才降级，且每一级都必须有一个"最终通向人"的出口。

## 二、为什么 OCR 排第一

| 理由 | 具体表现 |
|---|---|
| **抗缩放** | 同一段文字，窗口大小、分辨率、DPI 变了还是那段字；模板换个分辨率就废 |
| **加界面成本最低** | 新界面 = 往 JSON 里加几个关键词；模板要裁图、入库、调阈值、写 fixture |
| **可读、可解释** | 日志里能直接打"命中关键词：开始行动"，出错时一眼知道为什么 |
| **更适合做"防串台"** | 可以用 `require_all` 要求多个词同时出现（见下面的例子） |

而模板的失效条件很硬：换皮、位移、光照剧变都会掉分——所以它**只配做纯图标或美术字**的识别。

## 三、严格层和候选层：误召回可以忍，误点击不能忍

OCR 出来的结果分两级用：

- **候选层**（宽松）：关键词只命中一两个字 → 只写进诊断日志，**绝不触发点击、不构成界面判定**；
- **严格层**（确认）：完整关键词命中 → 才可以行动。

这条规则的意义：OCR 一定会读错几个字，**允许"看见了但不确定"，不允许"不确定还去点"**。

## 四、什么时候才用模板

三个场景，都是"文字这条路走不通"：

1. **纯图标**：没有文字的元素（还没找到好例子的，先按"图标"处理）；
2. **美术字 / 艺术字**：游戏里的标题常是设计过的字形，OCR 读不稳。真机上出现过两次：
   - 地图卡片"衔尾蛇行动"被读成"**衔尾衍动**" → 零号大坝卡片改用模板；
   - 特勤处底部"Tab 开始游戏"提示条被读成"**0 开 她 窮 观**" → 主标记改模板，OCR 只留兜底。
3. **按钮图标**：比如"确认配装"按钮，全帧 OCR 会丢"装"字 → 模板主定位 + 坐标兜底。

## 五、坐标是最后手段，而且必须验证

坐标直点（`strategy: coord`）最快，但最脆：UI 一改版就点到空气里。

所以规矩是：**用坐标点的，点完必须验证界面变了**。例如"烽火地带"卡片用坐标 `(348, 906)` 直点，点完立刻轮询"模式选择界面消失了吗"——没消失就重试/升级为人工。

> [!warning] 坐标不能"点完就算"
> 坐标点击本身没有识别能力，它的安全性完全来自**点击后的验证**。没有验证的坐标点击 = 盲点。

## 六、全失败怎么办：两条人工出口

| 出口 | 什么时候用 | 行为 |
|---|---|---|
| `pause` | 界面认识，但需要人确认（比如"入局提醒"里有没转移的安全箱） | 停下来，等回车；`--auto` 模式跳过 |
| `mark_unknown` | 完全不认识的界面 | 截图 + 界面候选 + 全帧 OCR 词表存进 `screenshots/unknown/`，然后提示人工 |

`mark_unknown` 很关键：它让"认不出"这件事**留下证据**，下次标定时直接拿这批截图补标记。

## 七、真实案例（都来自 `screens.json` / `elements.json` 的注释）

| 界面 / 元素 | 遇到的问题 | 最终策略 |
|---|---|---|
| 特勤处 `lobby` | "Tab 开始游戏"提示条 OCR 稳定误读 | 模板主标记（`lobby_tab_hint.png`）+ OCR 兜底 |
| 模式选择 `mode_select` | "烽火地带"是美术字，但"烽火地带/前往游玩/全面战役"可读 | OCR 四选一 + 坐标直点 + 界面消失验证 |
| 地图池 `map_pool` | "衔尾蛇行动"读成"衔尾衍动" | 模板主标记（`zerodam_title.png`）+ OCR 兜底 |
| 广场常态 `plaza_ready` | "配装"会命中配装界面的"确认配装"，串台 | `require_all: ["配装", "出发"]` |
| 确认配装按钮 | 全帧 OCR 丢"装"字 | 模板主 + 坐标兜底 |
| 局内背包 `match_backpack` | "剩余离"常被读成"刺余/离阎" | 改成 `require_all: ["本局收获", "胸挂", "背包"]` |

## 八、代价：慢

分层识别是准的，但慢：

| 动作 | 实测耗时 |
|---|---|
| 全帧 OCR | ~114ms |
| 区域 OCR（800×400 / 240×80） | ~89ms / ~54ms（固定开销占大头） |
| 单次全界面 `Detect` | ~600-700ms（约 7 次 OCR + 若干模板） |

所以后来加了三层"省"：

1. **具名区域**（`zones.json` 的 `zone_bottom_right` 等）——只 OCR 一小块；
2. **同帧词表缓存**——一次 Detect 里 OCR 从 16 次降到约 7 次；
3. **变更门**（`Vision/ChangeGate.cs`）——先做 1/6 缩略图帧差（约 2ms），画面没变就跳过整轮识别。

## 九、为什么写进数据表而不是代码

`elements.json` 里每个元素一个 `strategy`（`ocr` / `template` / `coord` / `color`），流程只写元素名。意思是：

- 某个按钮的识别方式要换（模板换 OCR、坐标换模板）→ **改一行 JSON**，流程和代码都不动；
- 想查"这个按钮凭什么能点到" → 打开 JSON 看它的 `strategy` 与注释（每条都写了实测依据）。
