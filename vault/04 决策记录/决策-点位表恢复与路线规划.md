# 决策：点位表恢复与路线规划

> [!info] 一句话
> 2026-10-21 起，重新允许用"出生点 → 撤离点"的计划路线，于是有了零号大坝的点位底库：**14 个出生点 + 4 个撤离点**。但它只是**坐标底库**，不是"照着跑就行"的脚本——执行时仍然是感知说了算。

## 一、从"废弃"到"恢复"

| 时间 | 点位表的状态 |
|---|---|
| 2026-09-26 | 用户定「全流程禁止预设路线」，`loot_points`（物资点位表）废弃，`zero_dam_points.json` 只留撤离点锚点 |
| 2026-10-11 | 数据清理落地，文件按该决定瘦身 |
| 2026-10-21 | 决策反转：允许「出生点 → 撤离点」计划路线；点位表重新需要内容 |
| 2026-10-21 | 官网截图 → 自动提取 → 用户核对，14 出生点 + 4 撤离点入库（schema v2） |

> [!note] 为什么这次只恢复"出生/撤离"、不恢复"物资点"
> 出生点和撤离点是**每局都要用的骨架**；物资点是"去哪捡"的答案，一旦写死就变成盲执行。这条边界在 [[决策-禁止预设路线与反转]] 里有完整讨论。

## 二、点位从哪来：三步，每步都能回查

### 第 1 步：用户标注截图

用户在官网地图工具上截了两张图：一张标出生点、一张标撤离点（绿色图标）。

用户同时说明了一件事：**只标常规 + 条件撤离点**，因为——

- 随机撤离点太浪费时间（要等它开）；
- 电梯撤离点可能被堵，而且要先开门，不值得规划。

### 第 2 步：截图对齐官方底图 + 自动提取

| 动作 | 做法 |
|---|---|
| 截图 ↔ 官方底图对齐 | 多尺度 NCC 求缩放 + 偏移；诚实修掉了两个自身 bug（缩放因子公式写反了、模板没去均值） |
| 互证 | 三张截图得到**同一个变换**：`k ≈ 1.150`、偏移 `≈(17, 197)`——互相印证才敢用 |
| 撤离点提取 | 绿色高饱和像素聚类 → **4 个簇**（和"2 常规 + 2 条件"吻合） |
| 出生点提取 | 该图**没有**高饱和像素（图标是白色系）→ 改用"亮且与干净底图不同"的差分 → **13 个面积均匀（189-209px）的簇** |

官网筛选面板显示 **14 个**出生点，自动提取只拿到 13 个——这 1 个差就是必须人工核对的原因。

### 第 3 步：用户核对

- 用户指出**右下角漏了 1 个**，补成 `S14`（备注写明"首轮提取因亮度阈值漏检"）；
- 撤离点命名逐条确认（含名称与类型）；
- 确认后写入 `data/zero_dam_points.json`（schema v2），并用测试钉住：`DataStoreTests.ZeroDamPoints_SpawnAndExtract_Calibrated`。

## 四、数据长什么样

每个点同时保存两套坐标：

```jsonc
{ "id": "E1", "name": "常规撤离点", "location": "东区隧道", "type": "常规",
  "x": 401959, "y": -754996,          // 世界坐标（与官网 getMapPos 换算一致）
  "map_px": [3154, 1927] }            // 官方底图 4096×3072 像素坐标
```

为什么两套都要：

- `map_px` 是定位器的直接输出（它算出来的就是底图像素）；
- 世界坐标是游戏/官网的口径，方便和攻略、官方数据对齐；
- 两者之间的换算关系写在 [[标定-地图坐标换算]] 里，公式验证过 1423 条标记有 1422 条落图内。

## 五、怎么用：三条规矩

1. **点位表是坐标底库**。它回答"出生点/撤离点在哪"，不回答"这一局该怎么走"——中间还差定位 + 路线 + 感知。
2. **路线是计划，感知是裁判**。执行时如果路线说往东、感知说有墙/有人/有交互提示，听感知的：停、绕、或交人工。
3. **绝不写成"必须按顺序执行"的脚本**。一旦有人把它当脚本用，2026-09-26 那条决策的教训就白吃了。

## 六、缺口与代价

| 缺口 | 说明 |
|---|---|
| **路线图还没产出** | 截至 2026-10-21 的文档记录："路线图尚未产出，产出后入数据表" ❓待确认是否已开始规划 |
| **只有一张图** | 零号大坝是唯一标定过的地图；换图 = 重新走一遍三步流程 |
| **标点交互未标定** | `match_map`（局内地图屏）界面能认出来了，但"点哪里标点、确认键是哪个、图标坐标是多少"还没标定（K0 清单 §2.4） |
| **出生点能否固定未知** | 如果每局随机出生，路线就得按"任意 S → 目标 E"生成，而不是一条固定路线（跑刀方案开放问题 2） |
| **维护成本** | 版本更新、赛季改动都可能让点位漂移；每张图都要人工核对一遍 |

## 七、和定位的关系

点位表 + 定位器 = "知道目标在哪 + 知道自己在哪"，两者凑齐，路线才有意义：

```
点位表（S1-S14 / E1-E4） ──┐
                           ├──→ 选一条 S → E 的路线 ──→ 切成若干"路点"
小地图定位（当前 map_px）──┘                                   │
                                                               ▼
                                                伺服：朝下一个路点走（感知兜底）
```

这条链目前只有两头（点位表、定位器）是通的，**中间的"路线生成 + 路点切换 + 到达判定"还没做**（K1 剩下的活）。
