# 标定：出生点与撤离点（14 + 4）

> [!info] 一句话
> 零号大坝有 **14 个出生点（S1-S14）** 和 **4 个可用的撤离点（E1-E4）**，每个都带世界坐标和底图像素坐标，存 `data/zero_dam_points.json`。
> 这是"出生点 → 撤离点"计划路线的坐标底库；路线是计划，走位仍由实时感知兜底。

## 怎么标定的

流程一句话：**用户官网截图标注 → 多尺度 NCC 对齐底图 → 颜色/亮度聚类 → 编号图交用户核对 → 写入 `data/zero_dam_points.json`**。

1. **用户提供两张官网截图**：
   - `zero_dam_extract.png`：绿色图标 = 撤离点；
   - `zero_dam_spqwn.png`：白色图标 = 出生点。
2. **截图 ↔ 官方底图对齐**：多尺度 NCC 搜索缩放（k 从 0.70 到 2.20，步长 0.05）＋位置。三张截图得到**完全一致**的变换：**k ≈ 1.150、偏移 ≈ (17, 197)** —— 三份独立结果互相印证，才敢用。
   > 过程里诚实修掉了自己两个 bug：缩放因子公式写反了、模板没有去均值。
3. **撤离点提取**：绿色高饱和像素聚类 → **4 个簇**（与"2 常规 + 2 条件"的预期吻合）。
4. **出生点提取**：该图**没有任何高饱和像素**（图标是白色系）→ 换成"**亮**（灰度 > 190）**且与干净底图差异大**（差值 > 50）"的差分 → 得到 **13 个面积均匀（189-209 px）的簇**。
5. **数量对不上 → 交用户核对**：官网筛选面板显示 **14 个**出生点，我们只提到 13 个。用户看图指出**右下角漏了一个**，补成 **S14**（共 14 个）。
6. 用户同时给定撤离点命名（东区隧道 / 西区公路口 / 坝顶 / 维修通道）；
7. 写入 `data/zero_dam_points.json`（schema v2，含 `type` / `location` / `map_px`），并用 `DataStoreTests.ZeroDamPoints_SpawnAndExtract_Calibrated` 钉住数量与关键值。

> [!bug] S14 为什么漏了
> 首轮用的是**固定阈值**（亮 > 190 且与底图差 > 50）。右下角那个图标没达到阈值，被直接滤掉。具体是"亮度不够"还是"与底图差异不够"，数据里没细分（❓待确认）——但归因是清楚的：**阈值法只保证大多数**。
> 这是"阈值法"的典型失败：**边界样本必须人工核**——所以第 5 步"拿编号图给用户看"不是可选项，是流程的一部分。

## 失效条件（何时需要重标）

| 变了什么 | 会怎样 | 要做什么 |
|---|---|---|
| 赛季改版改点位（增删/改名/挪位） | 路线规划走错 | 重新截官网图 → 重跑对齐 + 聚类 → 交用户核对 |
| 换地图 | 完全不同的一批点 | 每张地图单独标（`zero_dam_points.json` 只是零号大坝） |
| 官网重打底图 | 对齐参数 k / 偏移变了 | 重跑 `find_alignment`，三张图的一致性是验收标准 |
| 阈值法漏检（像 S14） | 少点 | 一定出编号图给用户核对，别信"数量自动对上了" |
| 游戏内点位名称改了（如"西区公路口"） | 语义对不上 | ❓目前以数据里的 `location` 为准，实测撤离记录写的是"西区公路" |

**怎么复核**：重跑 `ai-training/src/_verify_marks.py`，产出 `marks_verify.png`（图上编号 S1-S14 / E1-E4）和 `marks_verify.json`（底图坐标 + 世界坐标），把图给用户看一遍。
