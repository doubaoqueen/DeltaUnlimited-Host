# 标定：地图坐标换算（世界坐标 ↔ 底图像素）

> [!info] 一句话
> 官方数据里的坐标是**世界坐标**（几十万量级），底图是**图片像素**（4096×3072）。两者靠一组从官方 JS 里挖出来的公式互转：`bj=128`、`xB2=633.486755`、`yB2=632.722656`、`centerX=358155.6875`、`centerY=750191.75`，`z=4` 时 **16 像素/单位**。
> 验证方式很硬：1423 个官方标记里 **1422 个落在图内**。

## 数值

| 参数 | 值 | 含义 |
|---|---|---|
| `bj` | **128** | 地图边界基准（官方 JS 变量名 `BJ`，瓦片坐标的偏移量） |
| `xB2` | `81086.304688 / 128` = **633.486755** | 世界坐标 → 经度单位的横向比例 |
| `yB2` | `80988.5 / 128` = **632.722656** | 世界坐标 → 纬度单位的纵向比例 |
| `centerX` | **358155.6875** | 世界坐标中心 X |
| `centerY` | **750191.75** | 世界坐标中心 Y |
| `z` | **4** | 瓦片层级；`2^4 = 16` 像素/单位 |
| 底图尺寸 | **4096 × 3072** | 16×12 块 256px 瓦片拼成（`map_db`） |
| 像素范围 | x ∈ [0, 4096)、y ∈ [0, 3072) | 对应 lng ∈ [0, 256)、lat ∈ [-192, 0) |

**正变换（世界坐标 → 底图像素）**：

```
lng = 128 - (centerX - worldX) / xB2
lat = -128 - (centerY + worldY) / yB2
px  = lng * 2^z        # z=4 时 16px/单位
py  = -lat * 2^z
```

**反变换（底图像素 → 世界坐标）**：

```
lng = px / 2^z
lat = -py / 2^z
worldX = centerX - (128 - lng) * xB2
worldY = (-128 - lat) * yB2 - centerY
```

**验算（拿真实点位对一遍，别只信公式）**：

| 点 | 世界坐标 | 算出的 map_px | `data/zero_dam_points.json` 里的值 |
|---|---|---|---|
| S1 | (343938, -797007) | (1689.0, 864.2) | `[1689, 864]` ✅ |
| E1 | (401959, -754996) | (3154.4, 1926.5) | `[3154, 1927]` ✅ |

**整体自校验**：1423 条官方物资标记里 **1422 条**落在 4096×3072 内，且分布合理（x 974-3076、y 643-2222，四周留了边距）——公式与参数同时对了才会有这个结果。

## 三层坐标系统（最容易搞混的地方）

| 层 | 长什么样 | 谁在用 | 怎么转到下一层 |
|---|---|---|---|
| ① **世界坐标** | 几十万的整数，如 `343938, -797007` | 官网数据、`data/zero_dam_points.json`、路线规划 | 用上面的公式 → ② |
| ② **底图像素 `map_px`** | `0-4096 × 0-3072` | 官方底图、出生点/撤离点、定位器输出 | **没有直接换算**（要先知道小地图缩放） |
| ③ **屏幕/帧坐标** | `0-1920 × 0-1080`（设计分辨率） | 小地图面板、HUD、点击 | **没有公式级换算**：只有定位器把 ② 算出来后，伺服再把"地图上的目标"变成转向/前进动作 |

> [!warning] ② → ③ 不能直接算
> 定位器输出的是"**我在底图上的哪一点**"，不是"我该点屏幕哪儿"。从地图点到屏幕像素，需要"小地图的缩放比例 + 面板圆心"——而**缩放比例恰恰是未知的**（所以定位器要做多尺度搜索）。这就是为什么导航走的是"定位 → 规划 → 伺服转向前进"，而不是"算个屏幕坐标直接点"。

## 怎么标定的（其实是"从官方 JS 里挖出来"）

1. 找到官网地图工具的脚本（`js/lib/main.js`），里面有 `getMapPos` / `getSourceMapPos` 两个函数，公式和常量都在；
2. 抄下 `bj / xB2 / yB2 / centerX / centerY`，以及 Leaflet `CRS.Simple` 的"像素 = 坐标 × 2^z"；
3. 解析 `js/lib/map_article.js` 的 `mapArticle2/3/4`，拿到 **1423 条**物资点（含世界坐标、图标类型、大区域、条件）；
4. **用落图率自校验**：批量换算全部标记，看图内比例与分布；1422/1423 → 通过；
5. 反变换也在代码里实现并互验：`ai-training/src/_align_marks2.py` 的 `px_to_world()`（底图 → 世界）与 `map_px` 列互为逆运算。

## 失效条件（何时需要重标）

| 变了什么 | 会怎样 | 要做什么 |
|---|---|---|
| 官方底图换版本 / 赛季重打瓦片 | `centerX/centerY`、bounds 可能变 | 重新从 `main.js` 抄常量 + 重跑落图自校验 |
| **换地图** | 每张地图有**自己**的 bounds/center | **不能套用零号大坝的参数**，要各自挖 |
| `z` 变了（如 z=5） | 像素/单位变成 32 | 换算时同步改 `2^z`（瓦片也要重拼） |
| 官网前端改版（换了坐标系/接口） | 公式整体失效 | ❓待确认：需重新读 JS |
| 楼层图（`daba_0f/1f/2f`） | `bj=64`，与室外 `128` 不同 | 楼层坐标系**还没标定** → 见 [[标定-分层图层]] |
