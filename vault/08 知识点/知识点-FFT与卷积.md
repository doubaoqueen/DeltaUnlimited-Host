# 知识点：FFT 与卷积

> [!info] 一句话
> 大图上做模板匹配，本来是"模板在每个位置都算一遍"（慢）；FFT（快速傅里叶变换）把这件事变成"**先把两张图各算一次指纹，指纹一相乘，一次就算出全部位置**"（快）——结果是**完全一样的**，只是不再傻等。

## 为什么需要它（在这个项目里）

小地图定位是这条要求最狠的地方：

- 底图 **4096×3072**（官方零号大坝拼接图）；
- 小地图 240×240 左右；
- 还要在 **8 个尺度**上各搜一遍（150/180/210/245/285/330/380/440px）。

老老实实滑窗，一次定位要算**十几亿次乘加**，Python 里得跑几十秒——离线看报告可以，实时（8Hz）想都别想。用 FFT 之后，同样一帧的八个尺度在**几秒内**跑完（纯 Python + numpy），C# 侧再进一步提速。

## 原理（够用就好）

### 滑窗匹配其实是一种"卷积"

模板匹配要算的，是"模板和每个位置的局部图像的内积"。数学上这叫**互相关（cross-correlation）**，它和卷积几乎是同一件事（只是模板要不要翻转）。

所以问题变成：**怎么快速算一个卷积？**

### 卷积定理：时域卷积 = 频域相乘

这是信号处理里最漂亮的一条定理：

> 两个信号在"空间/时间"里做卷积，等于它们在"频率"里做**逐点相乘**。

打个比方：

| 做法 | 类比 |
|---|---|
| 滑窗（空间域） | 拿放大镜在照片上一格一格挪，每挪一次重新比一遍 |
| FFT（频域） | 先把照片和底片都"翻译成指纹"，指纹对上就是相乘一次，再翻译回来 |

具体三步：

```
F_img = FFT(大图)          ← 大图的"指纹"
F_tpl = FFT(模板)          ← 模板的"指纹"
结果图 = IFFT(F_img × conj(F_tpl))   ← 指纹相乘，再翻译回空间
```

`conj` 是共轭（虚部取反），因为我们要的是**互相关**而不是严格的卷积。

### 为什么快这么多

| | 滑窗 | FFT |
|---|---|---|
| 复杂度 | O(N·M)（N=大图像素数，M=模板像素数） | O(N log N)（跟模板大小基本无关） |
| 4096×3072 底图 + 240×240 模板 | 约 10¹² 量级 | 约 10⁸ 量级 |

关键洞察：**滑窗的代价跟模板大小成正比，FFT 的代价几乎与模板大小无关**。所以模板越大、图越大，FFT 赢得越夸张。小模板（比如 20×20 的图标）在小图上匹配，直接滑窗反而更快——FFT 有固定开销，别滥用。

### 积分图：另一个"一次算好"的技巧

NCC 除了分子（互相关），还需要分母里的**局部均值**和**局部方差**。这两个量也是"每个位置都要算一次"的东西，但可以用**积分图（summed-area table）**一次算好：

- 积分图上任意矩形的和 = 四个角一加一减（O(1)）；
- 于是"任意窗口的像素和"、"任意窗口的平方和"都能 O(1) 拿到；
- 均值 = 和 / 面积；方差 = 平方和/面积 − 均值²。

在本项目的实现里，这两件事其实是**用 FFT 一起做的**：

```python
c1 = corr(img, mask)        # 局部像素和（掩膜内）
c2 = corr(img * img, mask)  # 局部平方和
cN = corr(img, T0)          # 去均值后的互相关（分子）
var = c2 - c1*c1/N          # 局部方差（分母的一部分）
score = cN / sqrt(var * tE) # 归一化
```

`c1`、`c2` 用同一个 FFT 框架算出来，等价于积分图的作用——**一次变换，把分子分母全拿到**。这也是为什么 `_ncc_scores` 那个函数看着短，却在做四件事。

## 在本项目中的用法

| 位置 | 用法 |
|---|---|
| `ai-training/src/minimap_localizer.py` | `_ncc_scores()`：`np.fft.rfft2` / `irfft2` 算**完整得分图**（不取最大值），掩膜 NCC + 积分图 + 低方差屏蔽（`MIN_STD`） |
| 粗搜索降采样 | 底图先缩 `F=2`（4096→2048）再匹配，速度快 4 倍，位置再乘回 2——精度损失可接受 |
| 多尺度 | 8 个尺度各跑一遍 FFT 匹配，**取分数最高的尺度**（不是票数最多的，见下） |
| C# 版 `Vision/Localization/MinimapLocalizer.cs` | 改用 OpenCV `CCOEFF_NORMED` 的 `MatchTemplate`（内部已高度优化）；圆外填模板均值弱化 HUD 干扰 |
| **两版一致性验证** | 6 个标注样本 C# 与 Python **位置逐像素相同**；分数上 CCOEFF 比 Python 掩膜 NCC 低约 0.1-0.2（口径差，不是 bug） |

> [!tip] 一个很实用的对照
> 当你把算法从 Python 移植到 C# 时，"位置完全一致、分数差 0.1-0.2"就是**移植成功**的证据。如果位置开始不一致，先怀疑坐标系/通道序/掩膜，而不是怀疑数学。

## 常见误解 / 坑

> [!warning] 误解 1：以为 FFT 会改变匹配结果
> **不会。** 卷积定理是恒等变换，频域乘法算出来的就是空间域卷积的同一个数。差别只有两点：① 速度；② 浮点误差（可以忽略，但自检时要留容差，比如断言 `score > 0.9` 而不是 `== 1.0`）。
> 换句话说：**FFT 是加速器，不是另一种算法。** 如果结果变了，是你的实现错了（补零、边界、共轭、通道）。

> [!bug] 坑 2：边界与补零
> FFT 卷积默认是**循环卷积**——图像右边会"绕回"左边。所以必须把两张图补零到 `H+h-1 × W+w-1` 再变换，只取合法的重叠区域。`minimap_localizer.py` 里那句 `s=(sH, sW)` 和切片 `[:H-th+1, :W-tw+1]` 就是在干这件事。漏了会得到"贴边界的假高分"。

> [!bug] 坑 3：多尺度投票选错（本项目真实踩过）
> 一开始让所有尺度"投票"，取票数最多的位置。结果**小尺度在纯色区集体投给同一个错误位置（5 票），正确位置只有 2 票**。
> **修法**：改成"取分数最高的那个尺度"。用户之前确认过的三帧立刻全部命中。详见 [[坑-多尺度投票选错]]。
> 教训：多尺度搜索里，**分数**比**票数**可信——因为票数会被"低尺度在低纹理区乱投票"污染。

> [!bug] 坑 4：在低方差区域硬匹配
> 纯黑边框、一片天空，方差≈0，NCC 分母趋零，分数爆炸（实测出现过 28、346486）。必须给方差设下限并判无效。

> [!note] 坑 5：以为"快"就能实时
> FFT 让**离线**跑得动，但纯 Python 单帧多尺度仍是**秒级**，离 8Hz 还差得远。要实时得靠：C# + 降分辨率 + 限制搜索窗口（`LocalizePrior` 先验局部搜索）+ 尺度先验。速度问题不能只靠换算法解决，还要靠"少搜"。

## 一句话记住

**FFT 把"模板在每个位置算一遍"换成"两张图各算一次指纹，相乘一次搞定"——数学结果一模一样，只是快了几个数量级；再配积分图，连 NCC 的分母也顺手算完。**
