# 知识点：WASAPI 与 HRTF

> [!info] 一句话
> **WASAPI 回环采集**让你能"录到电脑正在播放的声音"（不需要麦克风、不碰游戏进程）；而"听出方向"分两档难度：**左右靠两个声道的音量差（容易），前后靠 HRTF 编码在频谱里的细微差异（难）**。

> [!warning] 本项目状态：未投入
> 这条能力只做了提案（`docs/声音感知提案.md`，2026-10-22 用户决定"暂不投入，作为未来能力立项"），**当前没有任何代码**，也不影响现行 K1 路线。本篇是原理储备，不是现状说明。

## 为什么考虑它（在这个项目里）

跑刀的核心是**避战**。现有感知里，"有人打我"要等**受击红屏**——那时已经挨了一枪。如果能听到**枪声/脚步声**，理论上可以早数秒做出反应（停住、改道、绕开）。

而且它天然合规：**录系统播放的声音，性质和截屏一样**——不读内存、不注入、不改游戏。这是提案里最重要的一句定位。

## 原理（够用就好）

### 采集：什么是"回环"

平时录音是"麦克风 → 声卡"，录的是**外面的声音**。
**Loopback（回环）** 是"声卡输出 → 偷偷复制一份"，录的是**你耳机里正在听的东西**。

```
游戏 → 声卡混音 → 耳机（你听到的）
                └──→ WASAPI Loopback 复制一份给程序（我们拿到的）
```

Windows 上两条现成的路：`NAudio` 的 `WasapiLoopbackCapture`，或系统自带的 `Windows.Media.Audio`。

三个关键事实：

| 事实 | 含义 |
|---|---|
| 延迟约 **30-80ms**（回环缓冲 + 分析） | 足够做"告警"级决策，不够做瞄准级（本项目也不需要） |
| 不碰游戏进程 | 与截屏同级，属于"看得见/听得见"的自动化 |
| **独占模式风险** | 若游戏用 WASAPI 独占模式输出，回环可能拿到**静音**——开工前必须先探测 |

### 方向：左右容易，前后很难

| 方向 | 难度 | 原理 |
|---|---|---|
| **左 / 右** | ⭐ 容易 | 立体声两个声道，左边响 → 左声道能量大。**直接读能量差就行** |
| **前 / 后** | ⭐⭐⭐ 难 | 前后在物理上"到两只耳朵的距离几乎一样"，能量差几乎没有；游戏用 **HRTF** 把前后编码进**频谱细节**里 |
| 精确方位角 | ⭐⭐⭐⭐ 很难 | 需要大量"已知方向"的标注数据训练，标注成本高 |

如果输出是 5.1/7.1，或开了 Windows Sonic / Dolby Atmos / DTS，方向会**显式分布在多声道**里，难度直接降一档。

### HRTF 是什么

**HRTF = Head-Related Transfer Function（头部相关传输函数）**。

人耳判断"声音在前面还是后面"，靠的不是音量，而是**耳廓、头部、肩膀对声波的滤波**：

- 声音从**前面**来 → 被耳廓"聚"一下，某些高频被增强；
- 声音从**后面**来 → 被耳廓挡住一部分，高频被削弱，还会产生细微的回声叠加。

这套"滤波特性"就是 HRTF。游戏引擎（或 Windows 空间音频）在渲染时，会把 HRTF 的滤波**预先算进音频**里——所以你用普通耳机也能听出前后。

**对程序的含义**：想用简单能量分析区分前后，**注定失败**。必须看频谱（比如 mel 频谱），而且最好用机器学习；并且它**依赖耳机型号和空间音频设置**——换个耳机、关掉空间音频，特征就变了。所以提案里写的是"需要按本机标定"。

> [!note] 一个容易忽略的限制
> 游戏里**队友和敌人的脚步/枪声很可能是同一套音效**。如果真是这样，声音只能得出"附近有人"，**分不出敌友**。对跑刀其实够用（一律当敌人避开），但精细决策就受限了。

## 红线：为什么"声呐透视"不能做

这是项目总红线的直接延伸（见 [[决策-红线与边界]]）。声音能力的边界写得很清楚：

**可以做**（"遇险即停 / 避战"原则内）：

1. 枪声检测 → 提前告警（比受击红屏早数秒），触发暂停/改道；
2. 脚步声 → 附近有人 → 停/绕（跑刀核心就是避战）；
3. 方向辅助避让：左侧枪声 → 后续路径避开左侧；结合定位轨迹可做"热点区"记忆；
4. 事件音校验：撤离倒计时/开门/拾取音，作为状态机的额外确认信号。

**不做**：

- ❌ 用声音**定位敌人并引导瞄准/交火**（战斗辅助）；
- ❌ "声呐透视"式的敌人精确位置显示。

一句话：**声音只做"感知 → 避让/暂停/改道"，不做"感知 → 交战"。**

为什么这条线这么硬：一旦允许"用声音算出敌人在哪、然后对准他"，性质就从"导航自动化"变成"战斗辅助"，整个项目的立论（只做界面导航、不碰对抗）就崩了。**技术能力不等于许可证**。

## 如果要做，路怎么走（提案里的四步，均未开工）

| 阶段 | 内容 | 预估 |
|---|---|---|
| **A0 录音采集器** | 新命令 `airesound`（或 `airecord --audio`）：WASAPI 回环录 WAV + 与帧时间戳对齐写 manifest | 1-2 小时 |
| **A1 实证分析** | 用录音验证：枪声/脚步能否检出、L/R 能量差可靠否、前后可辨否、队友/敌人可区分否（可用已有两局的已知事件时刻对照：00:08:19 受击、00:11:38 击杀播报、00:40:24 被淘汰） | 2-4 小时 |
| **A2 事件检测器** | mel 频谱 + 轻量 CNN 或阈值法：枪声/脚步/其他 → "事件 + 方向 + 强度" | 1-2 天（需标注数据） |
| **A3 接入决策** | 作为 `ServoLoop` 的危险信号（与红屏检测并列）→ Danger/暂停/改道；**不参与任何交战逻辑** | 半天 |

开工前还要确认三件事：① 音频输出形态（耳机/音箱？开没开 Windows Sonic？游戏内 stereo 还是 5.1/7.1？）；② 游戏是否用 WASAPI 独占模式；③ 红线边界再确认。

## 常见误解 / 坑

> [!warning] 误解 1："录系统声音 = 录音频设备"
> 不是。回环录的是**混音输出**，跟麦克风完全无关，也不需要在游戏里开什么开关（除了别用独占模式）。

> [!warning] 误解 2："立体声就能听出前后"
> 立体声**只有两个声道**，物理上无法直接编码前后。前后信息藏在 HRTF 的频谱细节里，简单能量分析看不出来。

> [!bug] 坑 3：以为"能听见就能定位"
> 混战环境（64 人）里事件会重叠，多事件分离（声源分离）本身是个难题。而且队友/敌人可能同一套音效。**先做 A1 实证，别先写检测器**——这正是提案把它排成第一优先的原因。

> [!note] 坑 4：忽略音频设置差异
> 音效受玩家设置影响（HRTF 开关、音量平衡、声卡虚拟化、空间音频）。换一台机器，阈值可能全部要重标。

> [!danger] 坑 5：把声音接到"瞄准/交火"
> 绝对红线。任何"声音 → 精确敌人位置 → 转向/开火"的链路，即使技术上可行，也不允许存在。

## 一句话记住

**WASAPI 回环 = 录"电脑正在播的声音"（不碰游戏、延迟 30-80ms）；左右靠声道能量差、前后靠 HRTF 的频谱差；这条线只准用来"避开"，不准用来"交战"。**
