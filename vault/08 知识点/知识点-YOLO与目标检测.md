# 知识点：YOLO 与目标检测

> [!info] 一句话
> 分类只回答"**这是什么**"，检测要回答"**这是什么、在哪、有多大**"——所以检测 = 分类 + 定位，代价是标注从"点一下"变成"画个框"。本项目**现在不做**，但把接口和素材池留好了。

## 为什么需要它（在这个项目里，将来）

可通行性三分类解决的是"**能不能走**"。但跑刀还有一类需求是"**那边有什么**"：

- 看见敌人/AI → 绕行（N5，避战）；
- 看见尸体袋 → 也是搜刮信号；
- 看见金光柱/物资高光 → 去捡；
- 看见可交互容器 → 去搜。

这些目标**位置不固定、数量不固定、外观有变化**，模板匹配不够用，OCR 也不适用（没有字）。这就是检测任务。

## 原理（够用就好）

### 检测输出什么

一张图进去，一堆"框 + 类别 + 置信度"出来：

```
[
  {"cls": "enemy_player", "bbox": [x1, y1, x2, y2], "conf": 0.87},
  {"cls": "loot_highlight", "bbox": [...], "conf": 0.64},
  ...
]
```

**框的格式**有两种常见写法，混用是 bug 之源：

| 格式 | 含义 | 用在哪 |
|---|---|---|
| `xywh`（中心点+宽高） | `(cx, cy, w, h)` | YOLO 训练标签、部分模型输出 |
| `xyxy`（左上+右下） | `(x1, y1, x2, y2)` | 画图、裁剪、OpenCV `Rect` |

本项目的坐标习惯是 **`xyxy` / `[x,y,w,h]` 混着出现**，所以每处必须写清口径（`ground.py` 的提示词里就明确要求 `bbox: [x1,y1,x2,y2]`，并要求 `x1<x2、y1<y2`）。

### IoU：判断"框得准不准"

**IoU（Intersection over Union，交并比）**：

```
IoU = 两个框的交集面积 / 两个框的并集面积
```

- 完全重合 = 1；完全不沾 = 0；
- 一般 **IoU ≥ 0.5** 就算"框对了"。

它是检测评估的基础：mAP@50 就是"IoU 阈值取 0.5 时的平均精度"。

### NMS：去掉重复框

模型经常对同一个目标输出好几个框（都框在附近）。**NMS（非极大值抑制）**的做法：按置信度排序，保留最高的，把和它 IoU 太高的其他框删掉，重复。

这一步在 C# 里要手写几十行（YOLO11 这类导出仍带 NMS 需求）；而 **YOLO26 的 NMS-free 端到端导出**可以直接解析"框+类"，对 C# 部署特别友好——这是 `docs/AI训练侦查报告.md` §4.2 里推荐它的主要原因。

### 为什么 YOLO 快

一句话：**一次前向就出全部框**（"You Only Look Once"）。早期的检测方案是"先提候选区域，再逐个分类"，慢；YOLO 把图切成网格，每个格子直接回归"这里有没有目标、框多大、是哪类"。

## 本项目为什么**现在**不做

| 原因 | 具体 |
|---|---|
| **标注成本高** | 每类 800-1500 个实例、1500-3000 张带框帧；框还要画准（30px 的图标对人是精细活） |
| **先解决导航** | K1 的目标是"落地→标点→跟随→撤离→结算"空手跑通。**撤离直通跑不通，检测做得再准也没用** |
| **红线** | 模型只做感知传感器，不持有决策权；避战检测属于"第二步"，得等感知框架稳 |
| **素材要先攒** | `airecord` 全帧录制就是为将来 YOLO 准备的（"全帧将来直接喂 YOLO"）；现在先攒，不急着训 |
| **预标注这条路已试过** | VLM 预标注 P0/P0.5 两轮都失败在细粒度图标上，结论是"不划算"（见下） |

## 与 VLM 预标注的关系：结论是"不划算"

原本的如意算盘：让本地 8B 视觉大模型先框一遍，人只做确认/微调，省下画框的人力。实测两轮：

| 轮次 | 做法 | 结果 |
|---|---|---|
| P0 | 整帧直问 | 框大 5-8 倍（143×213 vs 真图标 25-40px）、队友图标误标撤离点、`conf` 全 0.95-0.98 无区分度 |
| P0.5 | 两步缩放（粗定位 → 裁图放大 → 紧贴细框） | 框紧了（24×23px ✅），但**类别区分仍失败**（72 个框里混着队友图标/红 X/橙救援/蓝标记），且模型"自相矛盾地附和"；定位精度结构性受限 ±10-20px |

结论（2026-10-11 用户拍板）：**VLM 预标注线收兵**，UI 模板线回人工五步流程，`aiground` GUI 暂停；YOLO 线关闭（本轮 enemy/corpse/prompt 均 0 框）。详见 [[AI-VLM预标注探索]]。

一个特别值钱的副产品：**容器类别定义一开始就错了**。当时把"所有箱子"都算容器，用户指出"可交互容器 = 带白色高光、需要按 F 搜索的物体"。这条教训直接改写了类别定义——**做检测前，先确认"这个类别在视觉上到底长什么样"**，见 [[坑-容器类别定义]]。

## 如果将来要做，需要什么

| 项 | 具体要求 |
|---|---|
| **类别** | 第一版**宁少勿杂**：`enemy_player` / `enemy_ai` / `corpse_bag` / `loot_highlight`（光柱）。跑刀的核心诉求是"避开"不是"识别准"，**误报比漏报便宜** |
| **模型** | Ultralytics 线，YOLO11s 或 YOLO26s（NMS-free、CPU 快 43%、小目标改进）；从 COCO 预训练微调，`imgsz 640` |
| **数据量** | 每类 800-1500 实例，1500-3000 张带框帧；真机误报率达标为止 |
| **标注工具** | 本地首选 X-AnyLabeling（内置 SAM/Grounding DINO 辅助，直接导 YOLO 格式）；视频可用 SAM2 记忆传播（关键帧标一次，自动扩散几十帧） |
| **训练配置** | batch 16-32，epochs 100-150，默认超参起步，末轮关 mosaic；RTX 5070 本地几小时 |
| **部署** | 新增 `OnnxDetector`（现有 `OnnxRunner` 是单输入/单输出定长缓冲，检测头形状不同）；YOLO11 导出要在 C# 补几十行 NMS，YOLO26 的 NMS-free 可直接解析 |
| **节奏** | 伺服 5-10Hz 下每 2-3 帧跑一次即可（预算 10-20ms）；同样 observe-only 先行，预警接既有 Escalate/暂停人工路径 |
| **验收** | 每类 **mAP@50 ≥ 0.7**，且真机"每分钟误报次数"可接受，才准碰动作层 |

> [!tip] 一个便宜的替代方案
> 图标类目标（光柱、撤离点图标）用**自家模板匹配**预标注比通用大模型准得多（`docs/AI训练侦查报告.md` §3.4 原话："用自家模板匹配先预标，人工只做修正，比通用大模型实用得多"）。这已经是本项目的经验。

## 常见误解 / 坑

> [!warning] 误解 1："检测就是分类加个框"
> 训练/评估/部署三处都不同：损失函数（框回归 + 分类 + 置信度）、指标（mAP 而非 F1）、后处理（NMS）。**换任务类型不是换模型文件，是换一整套流程**。

> [!bug] 坑 2：`xywh` 与 `xyxy` 混用
> 最典型的后果：框整体偏移半个宽高，且"看起来只是有点歪"。YOLO 标签是归一化的 `cx cy w h`（0-1），画图要转成像素 `xyxy`，中间还涉及送图缩放换算——`ground.py` 为这个写了三层换算 + 离线 selftest 钉住。

> [!bug] 坑 3：类别定义含糊
> "容器"到底是"所有箱子"还是"带白高光的可交互箱子"？定义含糊 → 标注员各标各的 → 模型学到的是噪声。**先写一句能让人一看就判断的类别定义，再开始标。**

> [!note] 坑 4：以为"预标注能省 80% 人力"
> 只有在**预标注质量足够高**时才成立。P0.5 的实测是：框对了，类别错了——这种"半对"的候选比没有候选更费人力（要逐个改类别，比从零画还烦）。

## 一句话记住

**检测 = 分类 + 定位，靠 IoU 判准、靠 NMS 去重、靠 mAP 评估；本项目现在不做，是因为"先跑通撤离"比"看见敌人"更值钱，而且 VLM 预标注已被实测证明不划算。**
