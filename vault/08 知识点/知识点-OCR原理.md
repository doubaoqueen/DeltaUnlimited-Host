# 知识点：OCR 原理

> [!info] 一句话
> OCR 就是"**把画面里的字变成可比较的文本**"——机器人不需要真的"读懂"，它只要判断"屏幕上有没有出现『出发』这两个字"。

## 为什么需要它（在这个项目里）

界面识别的主力是 OCR，不是模板匹配。原因很朴素：

- "出发""配装""开始行动"这些**文案**，改版时通常不变；而按钮的**美术风格**经常变；
- 文案一改，OCR 那边只要改一个字符串；模板匹配那边得重新裁图；
- 而且 OCR 天然带位置信息（每个词的框），可以顺带定位要点的按钮。

于是 `screens.json` 里大部分界面靠"某区域出现某几个词"来认，`elements.json` 里大部分按钮靠"某区域出现某个词"来点。

## 原理（够用就好）

OCR 一般分两步（现代引擎大多一步到位，但概念上是两步）：

1. **检测（detect）**：先找出画面里"哪里有文字块"，给出一个个矩形框；
2. **识别（recognize）**：把每个框里的图像认成字符串。

生活化类比：**先圈出"这里可能是字"，再逐个"看图猜字"**。

识别那一步的内部大致是：把文字块切成一条条横线 → 再切成一个个字/词 → 对每个字形做特征分类 → 输出最可能的字符序列，最后用语言模型/词典纠正（"离阎"→"离开"这种）。

### Windows.Media.Ocr 的能力与脾气

本项目用的是 Windows 自带的 `Windows.Media.Ocr`（零额外依赖，不用装 PaddleOCR/Tesseract）。它的脾气得摸清：

| 脾气 | 具体表现 | 应对 |
|---|---|---|
| **中文按"字/词"切** | 返回的 `Lines → Words` 里，中文常常**一个字就是一个 word** | 所以关键词匹配不能只比"单个词"，要做**行内连续词拼接**（见下） |
| **字号太小不行** | 8-10px 的小字基本认不出 | 区域裁切后**放大 1.5 倍**再送（仅当宽高 ≤1700px） |
| **尺寸有上限** | 全帧放大到 2880px 会超过引擎 2600px 上限 | 只有"区域裁切"才放大，全帧不放大 |
| **深底浅字要反色** | 游戏 UI 多是深底浅字 | 灰度 → 若平均亮度 <128 则反色 → Otsu 二值化 |
| **要语言包** | 没装中文语言包直接创建引擎失败 | 失败时给出明确提示（设置→语言→中文→光学字符识别） |
| **艺术字会稳定误读** | 实测把"开始游戏"提示条读成"0 开 她 窮 观" | 艺术字的地方**老老实实用模板**，别跟它较劲 |
| **慢** | 全帧 OCR ~114ms，区域 800×400 ~89ms、240×80 ~54ms，单次全界面 Detect（约 7 次 OCR）**600-700ms** | 靠 [[知识点-工程实践]] 里的"变更门"（`ChangeGate`）避免重复扫描 |

放大还有个隐藏的坑：**放大后 OCR 返回的框是放大坐标系的**，必须除以 `scale` 才能映射回原图——漏了这一步，点击位置会偏 1.5 倍（`WindowsOcrEngine` 里有 `r.X / scale`）。

## STRICT 与"候选 + 混淆提示"：两层，别混

`OcrTextMatcher` 把匹配分成两层，这个设计是整个识别层的安全底座：

| 层 | 规则 | 权力 |
|---|---|---|
| **严格层（STRICT）** | ① 单个 word 包含关键词；② 同一行内"最小连续词窗口"拼接后包含关键词（框只覆盖构成关键词的那几个词） | **可以裁决**：触发点击、判定界面命中 |
| **候选层** | 全帧文本里出现了关键词的**任意一个字符** | **只报警不裁决**，附"命中词提示"供诊断 |

为什么需要"行内连续词窗口"：中文被切成一个字一个 word，`"未"+"装"+"配"` 三个 word 拼起来才是"未装配"。窗口还要**从左侧收缩**，让最终框只覆盖真正构成关键词的那几个字（否则点到的位置会偏到句子开头）。

为什么候选层不能裁决：只要出现一个"配"字就点"配装"按钮，误点率会高到不可用。项目里有条 ADR（#11）：**宽松候选永远不作为点击依据**。这就是"沾边的候选只告警"的工程实现。

## 为什么"能用 OCR 就不上模板"

| 维度 | OCR | 模板匹配 |
|---|---|---|
| 改文案 | 改字符串 | 重新裁图、重标阈值 |
| 改美术风格 | 不受影响（字还是那个字） | 直接失效 |
| 缩放/分辨率 | 较宽容（有预处理兜底） | 敏感（必须先归一到设计分辨率） |
| 艺术字/图标 | 容易误读 | 稳 |
| 速度 | 慢（几十到几百 ms） | 快（毫秒级） |
| 是否需要素材 | 不需要（只要知道文案） | 需要一张裁好的小图 |

所以项目的分层策略是：**OCR 主力（便宜、可维护）→ 模板兜底（艺术字/图标）→ 固定坐标最后手段（都失败就停）**，见 [[决策-识别分层降级链]]。

## 在本项目中的用法

| 场景 | 怎么用 |
|---|---|
| **界面标记**（`screens.json` 的 `markers`） | `type: ocr` + `keywords` + `require_all`。`require_all` 是**防串台**的关键：备战界面和配装界面都有"配装"两个字，只靠一个词会认错 |
| **元素定位**（`elements.json`） | `strategy: ocr`，如 `loot_prompt`（拾取提示）、`depart_button`（出发按钮） |
| **干员选择**（`pick_operator`） | 干员标签是**艺术字**，按 ≤760px 分段 OCR + 1.5 倍放大，按锚点距离优先识别目标段、命中即停；未命中时打印词表诊断 |
| **背包界面识别**（`match_backpack`） | 三词严格命中 `["本局收获","胸挂","背包"]`。原来用 `["剩余离","本局收获","胸挂"]` 复测失败——"剩余离"常被读成"刺余/离阎"等变体（见 [[坑-干员标签OCR不稳]] 同类问题）；改后三词实测均严格命中，且结算界面没有"胸挂/背包"，不串台 |
| **HUD 状态门**（`HudStateGate`） | 定位前先识别界面；命中全屏 UI（背包/地图/结算）就判"没有小地图"，跳过定位 |
| **`ocr` 诊断命令** | `dotnet run -- ocr <截图> [关键词]`：打印词表 + 严格/候选命中情况。**OCR 出问题先跑它** |

## 常见误解 / 坑

> [!warning] 误解 1："OCR 认得字，所以它读得懂"
> 它只给你字符串。语义判断在代码里（关键词表、`require_all`、区域约束）。模型/引擎**不知道**"出发"是个按钮。

> [!bug] 坑 2：只比单词，中文全挂
> 中文被切成单字，`"配装"` 永远不等于任何一个 word。必须做行内拼接——这是 `OcrTextMatcher` 里最长的那段代码存在的原因。

> [!bug] 坑 3：以为 OCR 稳定，实际同一句话两种读法
> "剩余离"会被读成"刺余""离阎"。所以关键界面要用**多个词 + `require_all`**，而不是赌某一个词。赌单词的代码在测试里可能过，在真机上会偶发失败。

> [!bug] 坑 4：放大后忘了除回 scale
> 症状是"点击位置总是偏右下 1.5 倍"。凡是"先 resize 再识别"的路径，都要检查坐标有没有换算回原图。

> [!note] 坑 5：全帧 OCR 很贵，别在轮询里反复跑
> 一次 Detect 600-700ms。等待界面时靠 `ChangeGate`（1/6 缩略图帧差约 2ms）先判断"画面有没有变"，没变就跳过——这是链路从"卡顿"变"跟手"的关键优化。

## 一句话记住

**OCR = 先圈字、再认字；本项目用它判断"屏幕上有没有这几个词"，严格命中才敢动手，沾边的只记录——中文按字切，所以要比"拼起来的整句"。**
