# 知识点：图像基础

> [!info] 一句话
> 电脑眼里的"图片"就是一个**数字表格**：每格一个像素，每个像素存几个 0-255 的数（通道）。所有视觉处理——裁切、缩放、换颜色空间、归一化——本质上都是在这个表格上做加减和搬运。

## 为什么需要它（在这个项目里）

这条链路上每一环都在跟像素打交道，而且**通道顺序、尺寸、压缩质量**任一出错都会变成"看起来正常但结果错"的隐形 bug：

```
窗口截图（BGRA 4 通道）
  → 裁 ROI（648×324）
  → 缩放到 112×224（模型输入）
  → BGR 转 RGB（模型要求）
  → /255 再减均值除标准差（ImageNet 归一化）
  → 喂给 ONNX
```

上面每一步都能单独出错，而且大多**不报错**。

## 原理（够用就好）

### 像素、通道、颜色空间

| 概念 | 人话 |
|---|---|
| **像素** | 图上一个点。分辨率 1920×1080 = 横 1920 个、竖 1080 个点 |
| **通道** | 每个点用几个数描述颜色。灰度图 1 个（亮度），彩色 3 个（红绿蓝），带透明度 4 个（+Alpha） |
| **位深** | 每个数用多少位存。8 位 = 0-255（本项目所有截图与模型输入都是 8 位） |

三种常见"颜色描述方式"：

| 空间 | 三个数是什么 | 什么时候用 |
|---|---|---|
| **BGR** | 蓝、绿、红 | OpenCV 的默认顺序（**注意不是 RGB**） |
| **RGB** | 红、绿、蓝 | 深度学习框架/模型的默认顺序（PyTorch、ImageNet 归一化） |
| **HSV** | 色相、饱和度、明度 | **按颜色找东西**时最方便："红色"在 HSV 里就是一个色相区间，在 RGB 里是三个数一起变，很难写条件 |
| 灰度 | 亮度 | OCR 预处理、模板匹配、帧差 |

> [!warning] BGR / RGB 搞反 = 本项目最经典的隐形 bug
> 症状：训练指标很好，实机表现像瞎了（红色当蓝色看）。
> 现实中的交接点：Windows GDI 截图给的是 **BGRA**；OpenCvSharp 读进来按 **BGR** 用；模型训练时用 **RGB**。所以 `PassabilitySensor.FillChw` 里必须有一次 `BGR2RGB`，`TemplateMatcher` 里必须有一次 `BGRA2BGR`。

### 缩放与插值

缩放不是"扔掉一些像素"那么简单，怎么算新像素的值叫**插值**：

| 插值 | 特点 | 用在哪 |
|---|---|---|
| 最近邻（Nearest） | 最快、最糊弄，会有锯齿 | 几乎不用（除非要保"硬边"） |
| 双线性（Linear/Bilinear） | 折中，最常用 | 一般缩放（`minimap_localizer` 缩底图） |
| 面积（Area） | 缩小时按覆盖面积平均，最不容易丢细节 | 大幅缩小（测试里把 300×300 缩成 240×240 用的就是它） |
| Lanczos | 最锐利，最慢 | 只用于"给人看"的预览图 |

缩小倍数很大时（比如 648×324 → 112×224，约 1/2.9 倍），插值方式对结果有真实影响——所以**训练端和推理端必须用同一种缩放语义**（本项目两端都是"先 Resize 到 INPUT_SIZE，再归一化"）。

### ROI 与裁剪

**ROI（Region of Interest，感兴趣区域）** = 我只关心画面里的一块矩形。裁出来单独处理，好处有三：

1. **快**：只算 648×324（约 21 万像素）而不是 1920×1080（约 207 万像素），少一个数量级；
2. **准**：把 HUD、天空、血条这些干扰关在门外；
3. **可控**：ROI 是**标定**出来的（本项目 `[592, 656, 648, 324]`，见 [[标定-可通行ROI]]），改它就能改"模型看哪里"，不用重训。

裁剪的坑全在**坐标系**：`Mat(frame, new Rect(x, y, w, h))` 里的 x/y 是**左上角**，而很多识别结果给的是**中心点**——两者差半个宽高，忘了换算就会整体偏移（见 [[知识点-坐标系统与地图]]）。

### JPEG 与 PNG

| 格式 | 有损? | 特点 | 本项目用在哪 |
|---|---|---|---|
| **JPEG** | **有损** | 体积小，压缩会丢细节、在边缘产生"振铃" | 录制帧 `airecord`（q80）、ROI 训练图（q80）、初筛送图（q85）、`logs/ai` 的 ROI 留证 |
| **PNG** | 无损 | 体积大，像素精确 | 诊断截图、标注结果、模板小图、底图拼接 |

有损压缩为什么重要：**训练图是 q80 的 JPEG，实况画面是游戏码流（也有压缩）**。如果训练端只见过"干净的 PNG"，实机就会因为压缩噪声掉点。所以 `dataset.py` 里专门有个 `RandomJpeg` 增广（p=0.5，质量随机 35-90）来对齐这个差异。

## 在本项目中的用法

| 位置 | 用到的图像知识 |
|---|---|
| `Capture/CaptureService.cs` | GDI 截图返回 **BGRA**；`CreateDIBSection` + 负高度 DIB 保证行序与 OpenCV Mat 一致 |
| `Vision/FrameTools.cs` | `Normalize`：把任意尺寸的帧缩放到**设计分辨率 1920×1080**，之后所有识别都在这个基准上做 |
| `Vision/TemplateMatcher.cs` | 4 通道 → 3 通道（`BGRA2BGR`），否则 OpenCV 直接抛异常 |
| `Vision/Ai/PassabilitySensor.cs` | 裁 ROI → Resize 112×224 → `BGR2RGB` → 逐通道 `(v/255 - mean)/std` → CHW 排列 |
| `ai-training/src/dataset.py` | `Resize` → `ColorJitter` → `RandomJpeg` → `Flip` → `ToTensor` → `Normalize`（**顺序很重要**） |
| 色判类信号（如受击红屏） | 走 HSV：`elements.json` 的 `color` 策略带 `rgb` + `tolerance` + `min_ratio`（"红色像素占比超过多少"） |
| `data/ai_vision.json` | `roi_jpeg_quality: 80`、`ring_mb: 2048`（ROI 留证图的环形缓冲上限） |

## 常见误解 / 坑

> [!bug] 坑 1：以为"尺寸不对没关系，反正会缩放"
> 会缩放，但**缩放的语义必须两端一致**。训练端不 Resize、推理端 Resize，就是 train/serve 偏斜——模型在训练时从没见过被压缩到 112×224 的图。`dataset.py` 里专门注释了"Resize 必须存在"。

> [!bug] 坑 2：以为"BGRA 和 BGR 差不多"
> OpenCV 的 `MatchTemplate` 遇到 4 通道会直接报错；模型预处理遇到 4 通道会把 alpha 当颜色通道算进去。**通道数不对，不是精度问题，是崩不崩的问题。**

> [!bug] 坑 3：先增广再缩放
> `dataset.py` 的顺序是 **先 Resize 再增广**。反过来（先 ColorJitter/RandomJpeg 再 Resize）也可以，但必须两端想清楚——最怕的是"训练时先缩后裁、推理时先裁后缩"，ROI 内容会差一圈。

> [!note] 坑 4：忽略 EXIF / 行序
> 有些图带 EXIF 方向信息，读进来可能是躺倒的；GDI 的 DIB 默认行序是自下而上，所以截图时用**负高度**让行序与 Mat 一致。这类问题表现为"图看起来是正的，识别全错"。

> [!tip] 一个好习惯
> 任何"图进模型但结果不对"的问题，第一步永远是**把送进模型的那张 112×224 小图存下来看一眼**。很多 bug（颜色反了、ROI 裁歪了、整张全黑）肉眼一秒就能看出来，比读代码快十倍。

## 一句话记住

**图片 = 数字表格；通道顺序（BGR/RGB）、尺寸、压缩质量三件事必须两端一致；ROI 决定模型看哪里，坐标决定你点哪里。**
