# AI-VLM 预标注探索（P0 / P0.5 实测与收尾）

> [!info] 一句话
> 想让 8B 的本地视觉大模型替人"先框一遍"，好省下 YOLO 标注的人力。两轮实测（P0 整帧直问、P0.5 两步缩放）都失败在**细粒度图标**上，于是按预案收兵：UI 模板线回人工，VLM 只留"粗定位"当实验能力。

> [!warning] 状态：已收尾
> 2026-10-11 用户拍板回主线（K0/K1）。本文是**历史记录**，不是待办。方案稿全文见 `docs/VLM预标注流水线方案.md`。

## 当初想省的是什么钱

YOLO 避战（N5）的标注成本极高：每类要 800-1500 个实例、1500-3000 张带框帧，还得画准。如果能先让 VLM 出一版框，人只做"确认/微调/驳回"，成本能降一个量级。方案里设计了两条出口：

| 出口 | 产出 | 谁受益 |
|---|---|---|
| A. UI 元素模板 | 裁好的小图 + `elements.json` 条目 | 界面自动化（现有链路） |
| B. 检测数据集 | 框 + 类别（YOLO 格式） | 将来"搜/打"相关识别（敌人/AI/尸体袋/光柱/容器） |

流程设计上分得很清楚：**Python 提框 → C# 图形审批 → 两条出口**。红线也写死了：离线工具、不进运行时、候选必须经审批入库。

## P0：单图整帧直问（2026-10-11，40 帧 → 36 帧出框，共 73 框）

样本是金帧优先、seed=42 可复现的 40 帧。结论：**不合格**。

| # | 症状 | 量化 | 根因 |
|---|---|---|---|
| 1 | 小图标框严重偏大 | `extract` 中位 **143×213px**（真图标约 25-40px，**大 5-8 倍**）；**96% 的框中心落在左上角小地图区** | **网格粒度**：Qwen3-VL 对 1280×720 只有约 **46×26** 的感知网格，30px 图标 ≈1 格，结构性框不紧，只能画"这一带" |
| 2 | 队友图标被误标成撤离点 | `extract` 出 **27 框**，远超每帧真实撤离点数 | 提示词没排除队友图标（带 1/2/3 的是自身+队友）；8B-AWQ 小图标的语义区分能力存疑 |
| 3 | 置信度没有区分度 | 全部 **0.95-0.98**，错的框和对的框一样高 | AWQ 4bit 小模型"不自知"——与 prescreen v2 的观察一致，这次实锤 |

方案稿里自认了三条设计失误，写得很诚实：

1. 单图整帧直问是 VLM 定位**最弱的用法**，一开始就该设计两步缩放；
2. 提示词没排除队友图标；
3. 把 prescreen 已知的 `conf` 缺陷带进了"高置信度自动通过"的设计。

### 顺带定版的一份词汇表

P0 还有个副产品：**撤离点图标到底长什么样**（用户提供地图图例截图 → 本地 VLM 读回 + 用户口述确认）：

- 撤离点 = 绿色"奔跑人形 / 右上箭头"图标（图例名就叫"撤离点"）；
- 灰色同形状 = "未开启撤离点"，**也算**撤离点；
- 图标右下角可能带小附加形状（表示撤离/载具要求），仍属撤离点本身；
- **排除**：带数字 1/2/3 的标记（玩家自己与队友，形状相似——P0 混淆的主因）、白色方框内带小十字（降落点）。

## P0.5：两步缩放（2026-10-11，35 帧 → 99 框）

对策是"先粗后细"：**粗步**整帧只框大区域（小地图面板/大地图面板，大目标模型擅长）→ **裁出原图区域放大 ≥4 倍** → **细步**要求"紧贴目标外缘出框 + 显式排除带数字队友图标" → 映射回原图坐标。

过程中先修了一个自己挖的坑：**窄高裁图爆上下文**。296×462 的裁图按"宽 1280"放大成了 1280×1998，图片 token **2764** 超过服务端 `--max-model-len 2048`，每帧报 400。修复方案是送图三约束——**宽 ≤1280 / 高 ≤2048 / 面积 ≤100 万 px**（≈1280×720 整帧的已知安全量），并写进 `--selftest` 回归。

结果分三栏看：

| 问题 | P0.5 实测 | 判定 |
|---|---|---|
| 框太大 | ✅ **解决**：`extract` 中位 **24×23px**（P0 是 143×213px）——放大策略生效 | 通过 |
| 类别区分 | ❌ **失败**：72 个 `extract` 框里仍混着带数字队友图标、红色 X、橙色救援、蓝色标记；模型**"自相矛盾地附和"**——理由里明写"内含数字 1""此处为橙色"，照样输出"符合撤离点定义"，排除条款压不住 | **能力不合格** |
| 定位精度 | ❌ **结构性受限**：30px 图标在送图里约 81px ≈ 3 个感知格，模型输出精度 ±1-2 格 ≈ 原图 **±10-20px**——框在图标附近但打不中 | 结构性受限 |

> [!bug] "自相矛盾地附和"是最要命的一种失败
> 它不是"看不出来所以给个低分"，而是"看出来了、还在理由里写出来了、然后照样判对"。这类输出**没法靠置信度过滤**，因为它的 `conf` 一样高。这也解释了为什么"高置信度自动通过"在这类任务上不成立。

## 结论与退路（按预案执行）

1. **UI 模板线回人工**：退回手动五步流程（`capture` → `crop` → `tplprobe` → `elements.json`/`screens.json` → `annotate` 复验），工具都现成，模板只几十张，一次性成本；
2. **VLM 线收缩**：保留"粗定位（大区域找得准）+ 世界物体粗框"当实验能力，**暂停 `aiground` GUI（P2）投入**；
3. **YOLO 线关闭（2026-10-11 用户判定）**：本轮世界物体召回很弱——`enemy` / `corpse` / `prompt` **均 0 框**，`container` 22、`loot` 5；而且用户肉眼判定 container 框大多落在"无白色高光的普通箱子"上，**容器类别定义从一开始就错了**（用户自认：可交互容器 = 带白色高光、需 F 键搜索的物体，不是所有箱子）。这条教训（"白色高光 = 可交互容器"）转入跑刀主线，K1 搜刮识别可用；
4. **换更大模型不可行**：32B AWQ 需约 18GB 显存（5070 只有 12GB）；云端 API 违反"数据不出机器"红线。

## 三条教训

1. **先问"这个模型擅长什么尺度"，再设计提示词。** 8B 模型能看懂"这是地图面板"，看不懂"这是 30 像素的绿色小人"。用整帧直问去要像素级框，是在跟模型的结构性限制较劲。
2. **提示词的每一条歧义都会变成系统性错误。** "框出撤离点"没排除队友图标 → 10 帧里 27 个误标；"紧贴目标外缘"没有尺寸参照 → 框大 5-8 倍。写 prompt 时要假设模型**不会**替你做任何推理。
3. **`conf` 不是置信度，尤其在小模型上。** 错的框 0.97、对的框 0.96，这种分数只能当装饰。任何"按分数自动通过"的设计，都必须先用实测证明分数有区分度。

## 一句话复盘

**这次探索不是白做**：它用不到一天的时间，换来三个确定结论（8B 不能做细粒度图标定位、容器类别定义要改、`conf` 不可信），并把"白色高光 = 可交互容器"这条视觉线索送回了主线。**P0 闸门的价值就在这——便宜地证明"不划算"，比昂贵地做出半成品划算。**
