# 坑：按 Tab 打开背包时，左上角不是小地图——定位器却给了 0.648 的高分

> [!bug] 症状
> 用户复核第 8 组定位样本（`m2d`，00:34:31）时说："**完全错误，左边甚至不是小地图**，我估计是我打开的背包键时的界面。"
> 定位器给出的结果是 **0.648 分 @ 尺度 180**——分数不算低，位置全错。
> 这类帧混进轨迹后还会制造"瞬移"：另一处实测出现过 **2 秒挪 1394px（≈265 m/s）**。

## 根因

两层，缺一不可。

**① 定位器不知道"现在该不该定位"**

按 Tab 打开背包时，是**全屏 UI**，左上角那块根本不是小地图，是背包界面的纹理。定位器照旧裁左上角去匹配 → 把 UI 纹理当小地图，得到一个"跟某块地形很像"的位置。分数高只说明"纹理和某块地形像"，不说明"这是小地图"。

顺带一个旁证：那次 2 秒瞬移的帧，OCR 读出来的是"破坏物资室铁门 / 行动地点：水泥厂 / 报酬 30000"——**行动接取站面板**。交互 UI 面板同样会污染小地图区域。

**② 识别背包的关键词本身不稳**

`screens.json` 里 `match_backpack` 原来要求三词全中：`["剩余离", "本局收获", "胸挂"]`。
但"剩余离"（剩余撤离时间）经常被 OCR 读成 **刺余 / 离阎** 等变体 → 严格匹配失败 → 就算装了状态门也认不出背包。

## 修复方式

**① 关键词改成"实测严格命中"的三个词**

```json
{ "type": "ocr", "keywords": ["本局收获", "胸挂", "背包"], "require_all": true }
```

- 三词实测都严格命中（`胸挂（容量 x/13）`、`背包`）；
- `require_all` 防串台："本局收获"在成功/失败结算也会出现，但结算界面没有"胸挂/背包"，三词齐备才认。

**② 新增 HUD 状态门 `Vision/Localization/HudStateGate.cs`**

定位前先做一次界面识别：

```
ScreenDetector.Detect(frame, screens, group: "match")
  → 命中 match_backpack / match_map / match_settlement_success / match_settlement_fail
    → 判定"没有小地图"，跳过定位
  → 识别不出任何界面 → fail-open（当正常 HUD 处理），交给轨迹过滤兜底
```

`localize` 和 `localizetrack` 两个命令都接了这道门；`LocalizerTests.Fixture_BackpackFrame_IsGatedByHudStateGate` 用**真机背包帧**把行为钉住。

**实测**：

| 帧 | 结果 |
|---|---|
| m2d（背包帧） | ⚠️ "该帧为对局内 UI 界面（`match_backpack`），没有小地图，跳过定位" ✅ |
| m2b（正常 HUD 帧） | 正常定位 ✅ |

## 教训（以后怎么避免）

> [!important] 先判断"该不该测"，再测
> 测量前的前置条件检查（状态门）比事后过滤便宜得多，而且不会污染中间结果。

1. **高分只能证明"图和模板像"，不能证明"这是同一类东西"。** 需要一道**独立的**"这是不是小地图"判断，而不是指望匹配分数顺带说明。
2. **界面标记要用"实测词表"。** OCR 会稳定地读错某些字（"剩余离"→"刺余"），设计标记时要拿真机帧跑 `ocr` 命令看它到底读成什么，不要用界面上"应该"有的字。
3. **fail-open 要写在注释里**：识别不出界面时按正常 HUD 处理，靠轨迹过滤兜底——这不是偷懒，是"宁可多算一帧，也不要因为识别抖动就停止定位"。
