# 坑：把"所有箱子"当容器，白标了 22 个框——游戏里能搜的只有带白光的

> [!bug] 症状
> YOLO 检测线的第一版类别表里，"容器（container）"的定义是"箱子"。
> VLM 预标注跑完，出了 22 个 container 框。用户肉眼一看："**这些大多是没白光的普通箱子，根本搜不了。**"
> 当天 YOLO 线关闭。

## 根因

**类别定义从一开始就错了。**

游戏里的"可交互容器"判据是：**表面带白色高光、需要按 F 键搜索**的物体。不是"长得像箱子的东西"。

我当时用的是**常识上的箱子**（木箱、铁箱、货箱），而游戏内的判据是**"有没有白色高光 / 能不能按 F"**。定义错了，后果是滚雪球：

| 环节 | 结果 |
|---|---|
| 预标注 | 框的是"箱子形状"，不是"能搜的东西" |
| 训练 | 模型学到的是形状特征，与"能否交互"无关 |
| 评估 | 指标再好也没意义——它学的不是我们要的东西 |

**调模型救不了定义错误。** 这也是为什么当天就决定关线，而不是"再训一版看看"。

## 修复方式

1. **类别定义修正**（用户纠正）：可交互容器 = 带白色高光、需 F 键搜索的物体。
2. **YOLO 线关闭**（2026-10-11 用户判定）。同一轮的世界物体 recall 也确实弱：`enemy` / `corpse` / `prompt` 均 **0 框**，`container` 22、`loot` 5。
3. **有价值的副产品被捞出来**：「**白色高光 = 可交互容器**」这条视觉线索转入跑刀主线（K1 搜刮识别可用），成了后续容器感知的关键判据，写进了待办。

## 教训（以后怎么避免）

> [!important] 类别定义要问用户要"游戏内判据"，不是常识
> 判据必须满足两个条件：**人一眼能看出来** + **和游戏交互一一对应**（白光 / F 键提示）。而不是"这东西叫什么"。

1. **先花十分钟确认定义，再花十小时标数据。** 定义错了，标注、训练、评估全是白干，而且**指标会很好看**（它在认真学一个错误的目标）。
2. **定义要落成文字**：类别名 + 游戏内判据 + 反例（"没白光的箱子不算"）。只放在脑子里的定义，下次还会错。
3. **"常识"是最滑的陷阱。** 越是你觉得"这还用问"的词（箱子、容器、敌人），越容易和游戏里的判定条件错位。
