# 坑：缩放"到宽 1280"把图放大成了 1280×1998，每帧都 400，一条都没落盘

> [!bug] 症状
> VLM 预标注脚本 `ground.py` 升到 v2（两步缩放：粗定位 → 裁图放大 → 紧贴细框）后跑批量：
> **每一帧都失败，产出 0 条**。日志只有一句干巴巴的 `HTTP 400 Bad Request` ——看不到任何原因。
> 而同一个脚本的上一版（整帧直问）跑得好好的。

## 根因

v2 的第 2 步要把粗框**裁出来、放大**再问一次模型，代码里写的是"放大到宽 **1280**"。

对一个 **296×462 的窄高裁图**，按宽度放大就等于：

```
scale = 1280 / 296 ≈ 4.32  →  1280 × 1998
```

而图片 token ≈ **2764**，服务端的 `--max-model-len` 是 **2048**（单图 + 提示词 + JSON 输出全在这 2048 里）。所以每一帧都超长 → 每一帧 400 → 一条都写不出来。

> [!warning] 关键认知：**只限"宽"是不够的**
> 图片 token 跟**像素总面积**成正比，不是只跟宽成正比。窄高图按宽度放大，面积会爆炸。

顺带还有第二个问题：`ask()` 只把 `Bad Request` 抛出来，把服务端说的具体原因（context length 超了）扔掉了——所以排查时看不到任何线索。

## 修复方式

**① 送图三约束**（`ai-training/src/ground.py`）：

| 约束 | 值 | 理由 |
|---|---|---|
| 最大宽 | 1280 px | 省显存、够看清 |
| 最大高 | 2048 px | 防超窄超高裁图 |
| 最大面积 | 1,000,000 px² | ≈1280×720 整帧的**已知安全量** |

缩放比取三者之比的最小值，所以窄高图会被"面积/高度"压住。改完 token 数与整帧同级（~900），永远不再爆。

**② 错误信息带出服务端详情**：捕获 `urllib.error.HTTPError` 后读 response body 一起打印，`400` 不再是一个无信息的数字。

**③ 自检回归**：`--selftest` 增加"缩放三约束"用例——窄高裁图（296×462）和整帧（1920×1080）都必须满足 `w≤1280 ∧ h≤2048 ∧ w·h≤1e6`。

**效果**：同一批帧重跑，细框实测 27-35px（P0 单图直问时的中位是 143×213px），框终于贴紧了。

## 教训（以后怎么避免）

1. **缩放要限面积，不只限宽/高。** 任何"限宽 1280"的规则，都该加一句"且面积不超过 X"。
2. **400/500 这种"服务器说的话"必须原样带出来。** 只显示状态码等于把根因扔掉——排查时间全花在猜上。
3. **约束要写成常量 + 回归测试**（`MAX_W` / `MAX_H` / `MAX_AREA`），否则下次改阈值又踩一遍。
4. 这类"每帧都失败"的现象有个共同点：**系统性失败 = 参数错，不是运气差**。别抽帧重试，去看参数。
